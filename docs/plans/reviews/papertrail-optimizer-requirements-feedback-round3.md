# Feedback: papertrail-optimizer-requirements (Codex review, round 3 — Part C6 phasing)

## Verdict
Blocked. C6 has the right instinct to phase adjudicator-only before full pipeline work, but it currently misdescribes key landed-code facts and overclaims baseline comparability. The plan needs a revision before an implementing agent can safely retrofit profiles or report the first Phase 1 number.

## Failure Modes
- Scenario | The Phase 1 transform writes one synthetic sub-claim whose text is the whole citing sentence and dumps all paper passages into `evidence[]`. | Why the plan misses it | C6.2 says the adjudicator will decompose sub-claims, but the current adjudicator prompt only adjudicates existing `sub_claims[]` and explicitly tells it not to search or read `content.txt`. | What to add | State the exact envelope schema: top-level fields, `source_mode`, `handle`, `claim_type`, `sub_claims[]` cardinality, line numbering, `attestation` behavior, and whether decomposition is deliberately disabled or handled by a new prompt.
- Scenario | Feeding all cited-paper chunks makes Phase 1 materially harder than the extractor path on focus and materially easier on recall. | Why the plan misses it | The plan says this is "precisely" Sarol baseline shape, but Sarol's model baselines used retrieved top-k evidence, while the staged corpus exposes mean ~72 chunks per cited paper. | What to add | A bias note before any result is reported: all-chunk input removes retrieval recall loss but burdens the adjudicator with evidence selection; this can bias Phase 1 vs Phase 2 in either direction and is not a clean test of "single agent vs extract-then-judge" unless evidence budgets are controlled.
- Scenario | A run is resumed with `--profile full` after starting as `adjudicator-only`. | Why the plan misses it | C6.3 gives the right rule, but the current dispatcher has no resume CLI, no `hard_fields={"profile": ...}`, and no run manifest profile field. The engine only enforces hard-field drift when the consumer passes it. | What to add | Require profile in the durable run summary hard fields, the adapter-owned run manifest, and both release payloads; include a negative resume fixture that expects `LoopStop`.
- Scenario | The per-call canary is enabled and silently changes the true cost/session count. | Why the plan misses it | C6.5's arithmetic counts only scored claims. The current Runner's canary, if configured, runs inside every `SarolRunner.run()` call, and the engine calls the Runner three times per iteration. | What to add | Decide whether the canary is once per optimization run, once per engine Runner call, or once per nested profile stage; then price it in `CostModel` and the C6.5 table.

## Contract Checks
- Owner repo: `paper-trail`. Surface: `experiments/sarol-2024/program-v0/manifest.json` plus the `program-v0` tag. C6.1's "freeze does not change" is viable only because profiles are consumer-side selectors over the same 8 manifest entries; the engine's materializer still sees all entries and `commit_new_version()` stages all committed entries. The plan should explicitly say the manifest/tag stay stable, while the profile changes only Runner stage dispatch and optimizer editable policy.
- Owner repo: `paper-trail`. Surface: `SarolProgramStore.editable_paths()`. The Part B2 amendment is not yet reflected in code: the current method returns every non-contract entry, and the optimizer context/prompt state the same five-file edit scope. A profile-aware edit scope is adapter-owned; `agentic-label-opt` has no profile field in `ManifestEntry`.
- Owner repo: `paper-trail`. Surface: `SarolRunner.run()` and nested `/sarol-eval-item --stage ...` command. Stage subsetting must be implemented here: today `STAGES` is global and every claim loops through extractor, adjudicator, verifier. The plan also needs to name whether `/sarol-eval-item` or `shape_input.py` writes `ledger/evidence/<claim_id>.json` before adjudicator dispatch.
- Owner repo: `paper-trail`. Surface: `experiments/sarol-2024/scripts/stage_claim.py`. C6.2 is correct that staging writes `pdfs/<citekey>/content.txt` and does not fetch from the network; the caveat is that `stage_claim.py --source corpus` uses pre-chunked `corpus.jsonl`, while `--source full` reads local `annotations/<Split>/references` text. The plan should pin which source mode Phase 1 uses.
- Owner repo: `paper-trail`. Surface: optimizer release schemas. C6.3 says profile is stamped into both release payloads, but `ReleasePayloadTrain`/`ReleasePayloadVal` are engine dataclasses without a profile field; the adapter can put profile into `task_config`/`breakdown`/`corpus`, but the plan must name the exact location and schema version bump.
- Owner repo: `agentic-label-opt` @ `6d621ac`. Surface: `run_loop(..., task_config=..., hard_fields=..., resume=...)` and `engine.resume`. The engine frontier and step-back logic compare plain scalar values (`_select_best`, `_regressed`) and know nothing about profiles, so C6.3 is correct as a warning. Enforcement is entirely consumer-side via run-summary hard fields and dispatcher refusal.
- Owner repo: `agentic-label-opt` @ `6d621ac`. Surface: `RunInputs`, `RunArtifacts`, `ScoreResult`, `MistakeCorpus`. The plan correctly relies on opaque adapter-owned artifacts, but C6.7 needs to respect the engine contract: `MistakeCorpus` exposes only `ref` and `counts`, so the per-claim corpus must be persisted by the adapter at `ref`, not added as new typed engine fields.
- Owner repo: `agentic-label-opt` @ `6d621ac`. Surface: `ProgramManifest`/`ManifestEntry` materialization and versioning. The engine has no per-entry `source` or `sha256` and no profile dimension; the current adapter strip-and-rehash pattern remains the right cross-repo boundary. C6 does not require an engine schema change if implemented as consumer-side profile selection.
- Owner repos: rad-eval, crc-extraction-agent, paper-trail, MedVAL as consumers of `agentic-label-opt`. Surface: shared release/frontier semantics. C6's profile stamp is a paper-trail-specific hard field, not a general engine concept; the plan should avoid implying engine support and should record that no cross-consumer breakage is expected because profile data rides in adapter-owned config/release content.

## Modularity vs. YAGNI
- Decision point | Profile registry. | Plan's current choice | Add `profiles.py` with `adjudicator-only` and `full`. | Modular alternative + the realistic use it serves | A small typed profile object is justified if Phase 2 is committed, because it drives three coupled decisions: stages, shaped input mode, and edit scope. | Recommendation | Keep the abstraction, but make it tiny and explicit; do not make a general plugin registry. Two named constants plus validation are enough.
- Decision point | `shape_input.py`. | Plan's current choice | New mechanical transform from `content.txt` to an extractor-shaped envelope. | Modular alternative + the realistic use it serves | Reuse `stage_claim.py`'s line-prefix and source-mode choices instead of reparsing benchmark rows; reuse the extractor output schema from `src/specs/verdict_schema.md` rather than inventing a new envelope. | Recommendation | Create only if it is the single owner of the synthetic evidence file. Otherwise fold it into the Runner or `/sarol-eval-item` to avoid a second staging pipeline.
- Decision point | Profile-dependent edit scope. | Plan's current choice | `profiles.py` consumed by `editable_paths()`. | Modular alternative + the realistic use it serves | `SarolProgramStore.editable_paths(profile)` can derive from profile-owned editable path lists and still reuse the existing contract-path partition. | Recommendation | Avoid duplicating "all non-contract paths" logic in both `profiles.py` and `SarolProgramStore`; one source of truth should own the profile path lists and validate them against the manifest.
- Decision point | Reusing the same adjudicator prompt. | Plan's current choice | Shape input instead of rewriting prompt to preserve Phase 1/2 comparison. | Modular alternative + the realistic use it serves | A profile-specific wrapper prompt or explicit prompt section for adjudicator-only would be more honest if Phase 1 really needs decomposition/search/attestation ownership. | Recommendation | Raise to author as a comparability decision. The current "same prompt" claim is not doing the work the plan says it does.

## Verification Gaps
- Missing profile-aware selftests: `adapter.py --edit-scope --profile adjudicator-only` should return exactly the adjudicator prompt and rubric guidance, while `--profile full` returns the five non-contract paths.
- Missing stage-subsetting runtime test: an `adjudicator-only` batch should produce exactly one nested invocation per claim plus whatever canary policy says, and command vectors should include only `--stage adjudicator`.
- Missing shape-input fixture: given a staged `pdfs/<citekey>/content.txt`, assert the exact generated `ledger/evidence/<claim_id>.json` bytes or a normalized JSON equivalent, including `section`, `line`, `snippet`, `source_mode`, `claim_type`, `paperclip_handle`, and absent/empty attestation policy.
- Missing baseline-comparability check: run/report separate fixtures for all-chunk input versus top-k evidence input, or explicitly mark the all-chunk Phase 1 number as not directly comparable to MultiVerS/GPT-4.
- Missing VAL-root negative control against actual wiring: after a real or fake engine iteration, attempt to read the concrete VAL run-manifest path from the optimizer scope that will be used in production, not just a generic `val/` directory name.
- Missing profile resume negative control: create a run summary with `profile=adjudicator-only`, resume with `profile=full`, and assert `LoopStop` before any Runner call.
- Missing cost selftest for profile arithmetic and canary overhead: current `CostModel` proves 1,926 sessions for full at TRAIN=10, but it has no profile selector and no canary term.

## Suggested Revisions
- Rewrite C6.1 to say the existing adapter is full-pipeline only and C6 must retrofit profile selection into `STAGES`, `_stage_command()`, `editable_paths()`, context docs, release payloads, and dispatcher CLI.
- Rewrite C6.2 around an explicit JSON fixture. The current prose is not enough to implement a validator-passing envelope, and it conflicts with the adjudicator prompt's "do not search/read source" contract.
- Replace the "directly comparable" Phase 1 claim with a narrower statement unless the input is constrained to the same top-k evidence condition as the baseline being cited.
- Correct C6.8's diagnosis: do not say the current default adapter shares one TRAIN/VAL root unless the plan also specifies the `output_root` configuration that makes that true.
- Add `profile` to `CostModel`, price `stages_per_claim` from the selected profile, and decide whether the canary is included in session counts.
- Update all landed optimizer-facing docs before any Phase 1 run; they currently tell the optimizer to edit extractor/verifier prompts and attack extractor-side indirect attribution.
- Fold the Open Questions scaffolding into the body. Keep only OQ5 or other genuinely unresolved decisions as questions.

## Questions For The Author
- Should Phase 1 be an apples-to-apples Sarol baseline condition using top-k retrieved/annotated evidence, or an all-chunks cited-paper-reader condition with a caveated comparison?
- Is the adjudicator prompt allowed to change for Phase 1 to own decomposition/search/attestation, or is preserving the exact frozen adjudicator prompt more important than making those duties explicit?
- Should the canary run once per optimization run or once per engine Runner call? The current optional Runner implementation does the latter if configured.
- Is `source_mode="pdf"` acceptable for a synthetic Sarol-corpus envelope, or should Phase 1 introduce a distinct provenance value to avoid pretending a PDF ingest happened?
