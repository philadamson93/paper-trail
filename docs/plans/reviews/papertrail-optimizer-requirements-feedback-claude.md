# Feedback: papertrail-optimizer-requirements (Fresh Claude Code review)

## Verdict

**Revise.** The branch/schema drift analysis, D-number citations, and most file/line-count claims are impressively accurate on git-verification. But Part A2 — the plan's own "most consequential open call" — has a real internal ambiguity about which verdict field the collapse table operates on, the plan fails to cite an existing, more-rigorous prior-art doc (`docs/plans/paper-tool-validation.md`) that already did much of this grounding, and it doesn't reconcile its A2 recommendation against the sibling engine plan's own Phase 2c verification wording, which currently describes a different (and, if A2 is adopted, stale) collapse. None of these block Phase 0 elsewhere in the engine plan, but they should be fixed before this plan's Phase 2c freeze is treated as authoritative.

A fresh implementer cannot write the collapse function without resolving this. | Evidence: `docs/plans/papertrail-optimizer-requirements.md:28,53-65` vs `src/specs/verdict_schema.md` (main) §"Sub-claims" (11-value list) and §"Overall verdict" (rollup rule minting `CONFIRMED_WITH_MINOR`) | Required fix: state explicitly that the collapse operates on `overall_verdict` (12 possible values), rename "native 11-way" → "native overall_verdict enum (12 values including the rollup-only `CONFIRMED_WITH_MINOR`)" throughout, and confirm the Scorer reads `verdict.overall_verdict`, not an aggregate over `sub_claims`.

## Failure Modes

- **Scenario:** paper-trail's proposed collapse excludes `AMBIGUOUS` from the frontier denominator ("reported as an abstention rate, not forced into a 3-way bucket"), but Sarol's own published 3-way collapse (confirmed in `paper-tool-validation.md:217` and `parse_verdict.py`'s `to_3way`) has no abstention concept — every gold-labeled instance lands in one of the 3 buckets. | Why the plan misses it: comparing a macro-F1 computed with an abstention carve-out against MultiVerS/GPT-4 baselines computed with no carve-out is not apples-to-apples — an adjudicator that abstains on hard cases can inflate its F1 relative to those baselines simply by dodging them. | What to add: either score abstentions as automatic misses when computing any number that will be compared to the MultiVerS/GPT-4 baselines, or explicitly caveat that the abstention-adjusted macro-F1 is not directly comparable and report both numbers.

- **Scenario:** Phil picks the *other* A2 branch (freeze `adjudicator-dispatch-sarol.md` instead of mainline). | Why the plan misses it: Parts B and C are written almost entirely against the mainline-plus-new-collapse assumption (B1's `task-and-scoring.md`, C1's `error_class_counts` naming, etc.); if the Sarol-variant branch is chosen instead, most of Part B/C's prose needs re-deriving, but the plan doesn't flag which sections would need rewriting under that branch. | What to add: a short "if the Sarol-variant path is chosen instead" note under A2 naming which downstream sections (B1, C1) would need to change.

- **Severity risk, not currently addressed:** cost/runtime blowup. Each claim triggers 3 full nested Claude-Code subagent sessions (extractor, adjudicator, verifier); the graduated-N ramp goes up to the full 2,141-claim TRAIN split. | Why the plan misses it: D45's "per-claim budget… 1.5× v1 default" is cited as reused, but the plan never states a concrete $ or call-count ceiling for a v0 run at N=2,141, nor a kill-switch if optimizer iteration cost runs away (each iteration potentially re-scoring against some/all of TRAIN). | What to add: a rough per-iteration cost estimate at each graduated-N landmark, and confirm D45's budget invariant is actually wired into whatever dispatcher script the engine's `Runner` calls for paper-trail.
