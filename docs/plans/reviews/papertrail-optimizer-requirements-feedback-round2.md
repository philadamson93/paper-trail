## Failure Modes
- Scenario: `PaperTrailProgramStore.manifest()` loads `manifest.json` and constructs `ManifestEntry(**entry)`. | Why the plan misses it: The JSON includes `source` and `sha256`, which are not engine dataclass fields. | What to add: A loader spec that maps only `path`, `freeze_policy`, `contract_file`, `optional`, verifies `sha256` separately, and resolves the two-source freeze before handing a manifest to the engine.
- Scenario: The first Sarol adapter smoke produces `overall_verdict=OVERSIMPLIFY`, then the existing schema validator retries and escalates as malformed output. | Why the plan misses it: The Sarol prompt mentions relaxed validation, but the plan never adds the validator/orchestrator work to affected files or Part C requirements. | What to add: A schema-variant validator fixture with one valid Sarol file, one mixed native/Sarol file, and one invalid-label file.
- Scenario: A run resumes after a one-time TEST unseal and immediately fails the engine tripwire because `final_eval` scans the whole ledger. | Why the plan misses it: C4 notes the ledger-scope problem but C3's `--confirm-unseal` design does not say whether final eval gets a fresh ledger, separate run id, or isolated audit file. | What to add: State the lifecycle for optimization ledger vs final-eval ledger and forbid reusing a ledger containing `final_eval` for further optimization.
- Scenario: `score_sarol3.score()` receives all invalid predictions and reports `micro_f1=0.0`, but the release still lacks a hard stop on `n_scored` or requested-count coverage. | Why the plan misses it: It guards degenerate 0/0.33/1.0 and always-ACCURATE, but not partial/missing output coverage. | What to add: Require `n_total == requested_count`, `n_invalid` surfaced in the primary release, and a smoke stop when a batch is partially unscored unless explicitly testing invalid-output behavior.
