TL;DR

This plan makes paper-trail the third consumer of agentic-label-opt, the shared agentic-optimization engine (rad-eval is #1, crc-extraction-agent #2, MedVAL #4). It pins a frozen starting program (program-v0), authors the optimizer's instruction surface, and specifies the TaskAdapter that plugs paper-trail into the engine's loop.

Parts A, B and C are implemented and pushed. The new Part C6 phases the experiment: optimize the verdict stage first against mechanically-selected evidence, then add the agentic extractor and measure the delta. The judge is held constant across every phase, which is what makes that delta mean anything.

Not runnable yet. /sarol-eval-item — the nested command the Runner dispatches once per stage per claim — does not exist. It is named as a Task 5 eval-arm deliverable and was never built. A preflight now fails loudly naming it, but no real scoring run can succeed until it is written. This, not the paid gates, is the blocker on a first curve point.

"Immutable" is entirely consumer-side. The engine's contract_file=True enforces presence only — nothing in it stops the optimizer rewriting a contract file's bytes. The guarantee is the adapter re-hashing those three against the manifest after every edit pass, and ContractGuardedAgent turning a mismatch into a nonzero exit. Placement matters: run_loop raises LoopStop on a nonzero agent exit before commit_version, so a mutated contract fails the iteration before anything is scored or frozen.

Rule 1 sandboxes the subagents. The optimizer reading TRAIN gold is the mechanism by which it learns, not a leak.

The metric, and the trap

Frontier scalar is 3-way macro-F1. Micro-F1 is reported but must never be the objective: for single-label multiclass it equals accuracy, and gold is 78.1% ACCURATE, so a do-nothing always-ACCURATE program scores micro 0.781 — beating both published baselines — while scoring macro 0.292.

ACCURATE                                              -> ACCURATE
OVERSIMPLIFY NOT_SUBSTANTIATE CONTRADICT MISQUOTE INDIRECT -> NOT_ACCURATE
ETIQUETTE INDIRECT_NOT_REVIEW IRRELEVANT              -> IRRELEVANT

Baselines: MultiVerS 0.52 macro, GPT-4 4-shot 0.45 macro. score_sarol3.py --selftest pins both figures so micro cannot be adopted by accident.

C6.0 — the constraint that drives everything

The adjudicator never reads the source paper. That is a stated design invariant of the frozen prompt, not an accident. Its input is exactly ledger/evidence/<claim_id>.json.

So "adjudicator-only" can never mean "the adjudicator reads the paper". Something must always select evidence. The profiles differ only in what does that selecting.

C6.3 — comparability, corrected

The first draft claimed Phase 1 is directly comparable to MultiVerS 0.52 and GPT-4 0.45 while feeding the adjudicator all ~72 chunks of the cited paper. It is not. Sarol's MultiVerS result used BM25 + MonoT5 top-20 sentences; their GPT baselines used top-5. And this repo's own paper-tool-validation.md:79 already defined the apples-to-apples condition as title + abstract.

Any Phase 1 number must be reported with its evidence condition attached. A macro-F1 without the k is not a result.

C6.4 — what the phases claim

Phase 1 establishes how well the frozen judge performs at a fixed, mechanical evidence budget. Phase 2 swaps the mechanical selector for the agentic extractor and measures the delta against Phase 1's optimized adjudicator. That delta is the paper's actual claim: does agentic evidence acquisition beat retrieval?

Confound that must accompany the comparison. The phases differ on more than agency: Phase 1 hands over a fixed top-k with no sub-claim decomposition and a null indirect_attribution_check; Phase 2 decomposes and populates that field. A Phase 2 win is not attributable to agency alone.

C6.8 — the mistake corpus is a repair, not a check

The landed implementation returns only MistakeCorpus(ref, counts), so the optimizer sees aggregate error classes but never which claims failed, what it answered, or what gold said. On a Tier-1-open split that is close to scalar-only optimization. The Scorer already computes the prediction/gold join and discards it; it must persist it and point corpus.ref at that file.

Part D — Interface feedback to the engine plan

What building this consumer taught the shared-engine effort. This is the part of the work whose value has already been delivered regardless of whether paper-trail's own curve ever runs: paper-trail is the first consumer whose Runner also spawns hooked Claude Code sessions, which surfaced engine gaps the other three consumers could not.

  • Runner cost is neither accounted nor enforced by the engine, and the Runner is called three times per iteration rather than twice.
  • The audit ledger carries no actor dimension, so a nested session's legitimate reads are indistinguishable from the optimizer's.
  • The final_eval tripwire scans the whole ledger rather than the current iteration, so one TEST unseal permanently poisons every later run reusing that ledger file.

Two of these would need engine changes and are deliberately not requested — crc settled Runner-cost bounding consumer-side, and paper-trail adopts that pattern.

Out of scope — what this plan deliberately does not do
  • Phases 3 to 5 of the plan-of-record — the paper-writing effort. The paused paper track stays paused; this plan scopes only to making paper-trail a validating third consumer of the engine.
  • A full training curve across the graduated-N ramp. Verification requires establishing a first real scoring run, not a complete curve.
  • Fine-grained 9-way evaluation as its own frontier — a reported breakdown only, since that axis has no published baselines.
  • Building the graduated-N split infrastructure or the Docker isolation substrate — both are engine-plan work, not authored here.

Gotchas

Micro-F1 is a trap that beats both published baselines while doing nothing

An always-ACCURATE program scores micro 0.781 against this gold distribution, versus MultiVerS 0.59 micro. Macro scores the same program 0.292. If micro rises while macro falls, the program is getting worse and the wrong number is saying otherwise.

NaN passes the engine's metric validation

PrimaryMetric checks isinstance only. A NaN frontier value makes _select_best order-dependent and makes _regressed return False, so step-back silently never fires. The adapter asserts finiteness before returning a ScoreResult.

The old cost table understated every rung by a flat ~$95

An iteration is three Runner calls: TRAIN, VAL, and the post-commit probe. A TRAIN-only estimate misses a fixed 2 x VAL every iteration — at VAL=316 with 3 sessions per claim that is 1,896 unaccounted sessions. At TRAIN=10 the "cheap iteration ~$7" figure is really ~$96, of which 98% is VAL.

The shortfall does not shrink as TRAIN grows. A mechanical profile cuts each row to a third.

The rollup ladder is optimizer-editable, so the validator reads it rather than hard-coding it

An earlier implementation weakened the rule to "overall appears among the sub-claims", which let a file whose sub-claims are CONTRADICT and ACCURATE roll up to ACCURATE. The validator now parses the strictness ladder out of the editable rubric and enforces worst-wins against it: the optimizer may reorder the ladder, but not contradict whatever ladder it declared. An unparseable ladder fails closed with ROLLUP_ORDER_UNPARSEABLE rather than silently skipping the check.

AMBIGUOUS is a counted miss, not a wrong-rubric rejection

It is a native verdict, so the obvious reading groups it with the wrong-rubric rejections. The frozen enum contract says otherwise in as many words: it survives in the shipped tool as a workflow flag, and the exit validator must reject it in a verdict field "exactly like any other out-of-enum label" — which means charged as a miss and counted, never raised.
