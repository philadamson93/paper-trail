## Goal

Define the paper-trail consumer of `agentic-label-opt` concretely, on the same three axes crc's sibling plan used:

1. **`program-v0`** — pin paper-trail's starting-point program (the dispatch-prompt bundle) that the engine plan's Phase 2c freezes and tags, resolving a branch-reconciliation problem first: the `sarol` branch's own prior optimizer design targets an older, now-superseded shape of the mainline pipeline.
2. **The paper-trail optimizer-prompt** — author the `context/*.md` analog to rad-eval's and crc's, reusing the *substantial* prior design work already sitting on this branch (`docs/plans/experimental-plan-of-record.md` and its dependents) rather than inventing it fresh.
3. **The paper-trail requirements** — enumerate the edit-surface, the per-iteration release, the mistake-corpus shape, and the sealed-split contract, as the concrete spec the engine plan's paper-trail `TaskAdapter` (Phase 2c) implements.

**Why now.** This is not a green-field authoring task the way crc's was. The `sarol` branch already independently designed — starting 2026-04-20, months before the `agentic-label-opt` engine-extraction effort existed anywhere — nearly the identical framework this engine plan proposes: a **tiered leakage discipline** (Train fully open / Val scalar-only / Test physically sealed, its decision "D24"), an **agent-only optimizer** with no human-in-the-loop (its "D22" — independently arriving at the same choice crc made for different reasons, per the engine plan's *Resolved 2026-07-15* #6), a **Python dispatcher + fresh-context eval subagent** split (its "D25/D26", matching the engine's `Runner`/`program_worker` shape), and a **macro-F1 + per-class-F1 scorer** with a committed per-revision results table (its "D1/D36"). None of that was designed *in response to* this engine plan. It is genuinely independent prior art, paused in 2026-04-29 to prioritize tool features instead. Reconciling it against (a) the mainline pipeline, which has since drifted (`repo-organization`, `feature-paperclip-first-architecture` both landed since the pause), and (b) the now-real `agentic-label-opt` `TaskAdapter` contract is exactly the "concrete consumer that validates the seam instead of guessing it" move the engine plan's own §459 risk calls for — a third time, from a structurally distinct angle (no PHI, no code in the optimized program at all, an optimizer whose "run" is nested agent invocation rather than a function or subprocess call).

Since Sarol is a per-claim (not per-sub-claim) benchmark, the Scorer needs `overall_verdict` — see Part A2. **No scorer against any labeled ground truth exists anywhere on `main`.** The canonical fixture, `examples/paper-trail-adamson-2025/` (87 claims, one of the user's own published papers), is a completed real run used for regression eyeballing — not a benchmark with gold labels.

**The `sarol` branch (this branch) already designed the missing scorer — against an older pipeline shape.** `docs/plans/experimental-plan-of-record.md` is the consolidated plan; the benchmark is Sarol, Schneider & Kilicoglu 2024, *"Assessing Citation Integrity in Biomedical Publications"* (Bioinformatics btae420) — 2,141/316/606 train/dev/test SciFact-format claim records, 8,515 cited-paper paragraph chunks, richer per-citation annotations with gold labels, fetched via `data/benchmarks/sarol-2024/download.sh` to **outside the repo tree** (`$PAPER_TRAIL_BENCHMARKS_DIR`, default `~/.paper-trail/benchmarks/`) specifically so the optimizer's filesystem exploration can never stumble onto gold labels. `experiments/sarol-2024/` holds a **Sarol-specific adjudicator prompt variant** (`prompts/adjudicator-dispatch-sarol.md`, emitting a **9-class rubric** distinct from mainline's 11-way enum — see Part A2) and scoring scripts (`scripts/parse_verdict.py`, `stage_claim.py`, `record_usage.py`) that read gold from **outside the repo** (`$PAPER_TRAIL_GOLD_DIR`) and are, per that script's own docstring, "the ONLY code that touches gold." **Critically: none of this was ever run to a real curve.** The plan-of-record's Phase 0 ("infrastructure-design complete") is as far as the effort got before the 2026-04-29 pause — Phase 1 ("Task 5: eval-arm build," the dispatcher scripts + invariant checker) was never started, and the "things to be honest about" list explicitly disclaims "N=5 not-a-result (initial smoketest, not a curve point)." So unlike crc's iter-5 (a real, measured Phase-13 baseline), **paper-trail has no measured baseline for either the mainline pipeline or the Sarol-rubric variant** — see the warm-start discussion in Part D.

## Part A — Pin `program-v0`

**A1. The `program-v0` fileset.** Unlike crc's multi-file config-plus-code bundle, paper-trail's optimizable program is **pure Markdown — no code artifact in the loop at all** ("the instructions *are* the program," a purer instance of the same pattern the engine plan already named for crc):

| Artifact | Role | Source | Freeze policy | Contains gold/PHI? |
|---|---|---|---|---|
| `src/prompts/extractor-dispatch-paperclip.md` | Pass-1 evidence extractor, in-corpus path | committed (`main`) | committed source | clean — no PHI ever (public papers) |
| `src/prompts/extractor-dispatch-pdf.md` | Pass-1 evidence extractor, fetched-PDF path | committed (`main`) | committed source | clean |
| `src/prompts/adjudicator-dispatch.md` **or** `experiments/sarol-2024/prompts/adjudicator-dispatch-sarol.md` | Pass-2 verdict adjudicator | committed — **variant = A2** | committed source | clean |
| `src/prompts/verifier-dispatch.md` | Pass-3 attestation verifier | committed (`main`) | committed source | clean |
| `src/specs/verdict_schema.md` (+ `experiments/sarol-2024/specs/verdict_schema_sarol.md` if the Sarol variant is chosen) | the rubric — threaded to the Scorer as `task_config`, the same role crc's `task_definition.md`/`column_map.json` play | committed | committed source | clean |

Everything else in the pipeline (the orchestrator `paper-trail.md`/`ground-claim.md`, ingest/render scripts, validators) is **fixed runner code, not editable program** — *unless* Part D's topology-freedom question is resolved the other way (see Open Questions §3). No PHI-clean-vs-regenerated tension exists here at all (unlike crc's `spec_*.json`): the benchmark is public, so every artifact above can simply be committed as-is. This makes paper-trail's `program-v0` freeze structurally the **simplest** of the three consumers — a plain globset freeze, no scratch-first `/phi-vet` step, no hash-only reconstruction contract.

**A2. Adjudicator variant — the crux decision (genuinely open, Phil's call, mirroring crc's A2).** Two candidates, both real, neither measured:

- **Mainline `adjudicator-dispatch.md`** (native `overall_verdict` enum). *For:* this is the actual, currently-maintained product — improving it is the real point, matching the engine plan's own "validate against real proven work" framing; it has continued to receive engineering investment (paperclip-first awareness) the frozen Sarol variant lacks. *Against:* no scorer exists for it against Sarol today — one has to be built (see below).
- **`experiments/sarol-2024/prompts/adjudicator-dispatch-sarol.md`** (Sarol's own 9-class rubric, emitted directly). *For:* a scorer (`parse_verdict.py`) and a 9-way→3-way collapse table already exist for it. *Against:* it predates `paperclip-first-architecture` and `repo-organization` — its prompt likely references stale paths and doesn't know about `source_mode`; it was never actually run to completion either, so "has a scorer" is not the same as "has a measured baseline"; and optimizing it would mean improving a rubric variant the shipped tool doesn't use.

**Prior art this recommendation builds on and must reconcile with.** `docs/plans/paper-tool-validation.md` (this repo, `main`) already drafted a native→Sarol-3-way collapse (`CONFIRMED→ACCURATE`; `OVERSTATED`/`UNSUPPORTED`/`CONTRADICTED`/`MISATTRIBUTED`→`NOT_ACCURATE`; `CITED_OUT_OF_CONTEXT`→`IRRELEVANT`; `AMBIGUOUS`→exclude), plus real, already-collected label-frequency statistics over **1,873 Sarol dev+test evidence annotations**, and named target baselines: **MultiVerS 0.59 micro / 0.52 macro F1** and **GPT-4 4-shot 0.65/0.45** (abstract-only variant, apples-to-apples with Sarol's own published setup). That draft predates four verdict values this repo's rubric has since grown (`OVERSTATED_MILD`, `OVERGENERAL`, `PARTIALLY_SUPPORTED`, `INDIRECT_SOURCE`) — the collapse below supersedes it for those values — but the frequency table and baselines are reusable today, no new run required, and anchor both the collapse's correctness check (Open Questions §2) and the "first real scoring run" success criterion (Verification), rather than inventing a fresh bar.

**Recommendation (not locked — flag for Phil, per the pattern crc's A2 followed):** freeze **mainline's current prompts** as `program-v0`, and **port the Sarol-rubric collapse logic forward as a Scorer-side mapping layer**, not as a competing adjudicator prompt. Concretely: build a **new** native `overall_verdict` → Sarol-3-way collapse — this operates on the **12-value `overall_verdict` field** (the 11 sub-claim verdicts plus the rollup-only `CONFIRMED_WITH_MINOR`), not `sub_claims[].verdict` directly, since Sarol labels per-claim (the mapping below is a first pass, not final):

```
overall_verdict                                 → Sarol 3-way
CONFIRMED, CONFIRMED_WITH_MINOR                 → ACCURATE
OVERSTATED_MILD, OVERSTATED, OVERGENERAL,
  PARTIALLY_SUPPORTED, UNSUPPORTED,
  CONTRADICTED, MISATTRIBUTED, INDIRECT_SOURCE   → NOT_ACCURATE
CITED_OUT_OF_CONTEXT                            → IRRELEVANT   (Sarol's own doc: "closest in Sarol is ETIQUETTE")
AMBIGUOUS                                       → excluded from the frontier denominator; reported as an abstention rate, not forced into a 3-way bucket
```

**Abstention caveat.** Sarol's own published 3-way collapse has no abstention concept — every gold instance lands in one of the 3 buckets. Excluding `AMBIGUOUS` from this collapse's denominator makes any macro-F1 computed this way **not directly comparable** to the MultiVerS/GPT-4 baselines above unless abstentions are also scored as misses. Report both an abstention-adjusted number and a misses-included number whenever the comparison is drawn (see Verification). **Pin the naming now:** `primary_metric` = the abstention-adjusted macro-F1; the misses-included variant is a named field in `breakdown` (e.g. `macro_f1_misses_included`), not a second untitled number.

**Implementation note.** This mapping is new code, not a migration of `parse_verdict.py`'s existing Sarol-9-class collapse (that collapse stays as-is for the Sarol-variant path, per Part D's reuse framing). Model it as a sibling script — e.g. `experiments/sarol-2024/scripts/collapse_native_to_sarol3.py` alongside `parse_verdict.py`/`stage_claim.py`/`record_usage.py` (proposed name, not locked) — factored so the dispatch shape (verdict-in, bucket-out) mirrors `parse_verdict.py`'s existing collapse function rather than diverging gratuitously.

This keeps the optimized program = the real, single, currently-shipping adjudicator (simpler `ProgramManifest`, one prompt not two candidate prompts), and makes the Sarol-specific work **adapter-owned scoring logic** — directly analogous to how the engine plan required crc's `event_f1_at_W` to be **net-new scorer code**, not a straight port of `05_score.py`. **This mapping is a proposal, not a resolution** — Phil should confirm it (or pick the Sarol-prompt-variant path instead) before Phase 2c's freeze; see Open Questions §1.

**If Phil picks the Sarol-rubric variant instead:** Part B1's `task-and-scoring.md` and Part C1's `error_class_counts` naming are both written against the mainline-plus-new-collapse assumption above and would need re-deriving against the existing 9-way rubric + `parse_verdict.py`'s own collapse — flag this before starting Part B/C work if A2 resolves the other way.

**A3. Reconstruction / branch reconciliation.** **Git-verified 2026-07-20: `sarol`'s checked-out worktree does not have the `src/` tree at all** — `repo-organization` and `feature-paperclip-first-architecture` landed on `main` only. `sarol` still has the pre-restructure layout: real files at `.claude/prompts/{extractor-dispatch.md (single, pre-paperclip-split), adjudicator-dispatch.md, verifier-dispatch.md}` and `.claude/specs/verdict_schema.md` (pre-1.1). On `main`, `.claude/prompts` / `.claude/commands` / `.claude/specs` are symlinks into `src/prompts` / `src/commands` / `src/specs` — the real files live under `src/`. So `git diff main sarol -- src/prompts/` will show the **entire directory as absent on `sarol`**, not a small drift — that's expected, not a stop condition. **Freeze `program-v0` by reading the A1 files directly from `main`** (`git show main:<path>` or `git checkout main -- <path>` into the frozen destination) — do **not** merge or rebase `sarol` onto `main` (pulls unrelated tool-feature history onto a paused research branch) and do **not** treat `sarol`'s existing `.claude/prompts/extractor-dispatch.md` as a starting point to diff against — it is superseded by the paperclip/pdf split, not a predecessor of it.

## Part B — Author the paper-trail optimizer-prompt

**What's already designed vs. what's new.** Unlike crc, where the `context/*.md` layer was authored from scratch against `INSTRUCTIONS.md`'s framing, `sarol`'s plan-of-record already speclos a near-identical artifact: Phase 1's deliverable list names a **"`program.md`-equivalent optimizer instruction document"** (`experiments/sarol-2024/optimizer/program.md`, its "D42," explicitly modeled on the Karpathy autoresearch structure — note: `experimental-plan-of-record.md` reuses "D42" for a second, different decision in its decision-log table ("Autoresearch direct-lifts adopted…"); a pre-existing numbering collision in the source doc, not this plan's error, flagged for whoever maintains that log) and a **"5-column `results.tsv`-equivalent per-revision table."** This Part is therefore mostly **reconciling and porting forward what `sarol` already speclos**, adapted to the engine's concrete `TaskAdapter` shape, not fresh authorship.

**B1. The `context/` reference docs** (new, in `experiments/sarol-2024/optimizer/context/`, mirroring the engine's rad-eval/crc precedent):
- **`context/playbook.md`** — the iteration procedure. Reuse `sarol`'s own settled decisions directly: agent-only, no HITL (D22); dispatcher-as-Python-script, not agent (D26); uniform headless invocation across train/val, same subagent, output routed differently by the dispatcher (D27/D28); the **warm-start note** — see Part D's new third case, since neither candidate `program-v0` has a measured baseline, iteration 1 must *establish* one empirically before it can characterize it.
- **`context/task-and-scoring.md`** — the frontier scalar (macro-F1 over the 3-way collapse, per `sarol`'s own D1/D36 — this is *already decided*, not novel here) plus the per-class F1 breakdown; the error taxonomy — `sarol`'s own named failure modes are a real head start: the **INDIRECT-detection failure mode** (Contribution #6) and the **severity-under-commitment pattern** (its "s4," tentative, pending N=50+ data) are exactly the kind of adapter-owned error-class taxonomy crc's Part D #6 required; import them rather than inventing new classes.
- **`context/release-format.md`** — the per-iteration data contract (Part C1).

**B2. The hot-path prompt** (`experiments/sarol-2024/optimizer/prompt/`, the adapter's `agent_instructions`): objective (maximize macro-F1 on held-out Val); edit/read/sealed scope — EDIT = the `program-v0` globset (Part A1); READ = the release + a sampled slice of the mistake corpus + continuity docs; SEALED = Val/Test claim records and gold labels, which `sarol`'s design already keeps **physically outside the repo tree** (`$PAPER_TRAIL_BENCHMARKS_DIR`/`$PAPER_TRAIL_GOLD_DIR`) — a stronger sealing guarantee than either rad-eval or crc build, since there is no in-repo directory for the optimizer to be denied access to in the first place. Include the **per-claim budget** discipline `sarol` already speclos (its "D45," model-call-count primary, 1.5× v1 default) and the **round-trip sanity canary** (its "D46," guarding against a silently-broken scorer) — both directly reusable, not novel. **Cost/runtime risk (not yet estimated):** each claim triggers 3 full nested Claude-Code subagent sessions, and the graduated-N ramp goes up to the full 2,141-claim TRAIN split — a rough per-iteration $ estimate at each graduated-N landmark (10/25/50/100/200/2,141) is needed before a real run, plus confirmation that D45's budget ceiling is actually wired into whichever dispatcher script the engine's `Runner` calls (not just cited as reused); see Verification.

**B3. Continuity docs.** `sarol`'s `NEXT.md` + committed `results.tsv`-equivalent + an analysis notebook already serve much of this role; the one genuine gap versus crc/rad-eval's pattern is a `meta-learnings.md`-equivalent (confirmed/pending/reverted fixes across iterations) — add this new, small file; everything else ports forward.

## Part C — Requirements enumeration (the paper-trail `TaskAdapter` substance)

**C1. The per-iteration release** (paper-trail's analog to rad-eval's `ExtractionTrainRelease` / crc's release, aggregates-only): `metrics` (`primary_metric` = abstention-adjusted macro-F1, per Part A2; `breakdown` = per-class F1 + the 3-way confusion matrix + `macro_f1_misses_included`); `error_class_counts` (INDIRECT-detection misses, severity-under-commitment instances, per `sarol`'s named failure modes); `followups` (prior change-note's targeted verdict classes, prev-vs-current deltas); `frontier` (best-vs-current macro-F1 pointer); `budget` (cost-per-claim in USD — `sarol`'s `parse_verdict.py` already has a real `PRICING` table and `estimate_cost_usd` function; reuse it directly as the single source of truth — do not re-derive cost logic in the optimizer prompt or release builder; more load-bearing here than for crc since every subagent call is a full metered LLM invocation, not one call per pipeline stage); `prior_change_note`; on-demand full mistake corpus; Val aggregate-only (`extra="forbid"`-guarded, no per-claim gold visible). The exact typed `ReleasePayload` dataclass (field names, version field, `extra="forbid"` enforcement) is owned by the engine's Phase 0, which hasn't landed as code yet — this list is the field-level content paper-trail's adapter populates into that contract once Phase 0 exists, not a competing schema.

**C2. The mistake corpus.** Per-claim adjudicator reasoning + extractor evidence quotes + verifier bounce history. **No PHI anywhere** — the cited papers are public biomedical literature — but per the engine's OQ5 pattern (mistake corpus = adapter-owned opaque blob), the engine still shouldn't type its structure; the *reason* for sealing here is leakage-of-gold-labels, not privacy, which is exactly the generalization the engine plan's *Resolved 2026-07-20* #15 names. TRAIN-side mistakes are fully open to the optimizer per `sarol`'s D24 (Tier 1 = fully open) — no isolation nuance needed the way crc's PHI-in-a-network-denied-container framing required.

**C3. Sealed TRAIN/VAL/TEST split — already fully specified, unlike crc's.** `sarol`'s D13/D24 already lock this: graduated-N nested TRAIN subsets (10/25/50/100/200/2,141 full), a fixed VAL (316, dev split), sealed TEST (606) unsealed exactly once via a `--confirm-unseal` tripwire at landmark evaluation. Benchmark data lives **outside the repo** by construction (Part A/B above) — the strongest sealing guarantee of the three consumers, since there's no in-repo TEST directory to deny filesystem access to at all. This Part **confirms** the contract rather than designing it from scratch — the one open item is reconciling the split's provenance format against the mainline pipeline's current claim/citekey identifiers (a mechanical mapping, not a design question).
