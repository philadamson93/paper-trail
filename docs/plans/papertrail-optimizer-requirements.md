## Goal

Define the paper-trail consumer of `agentic-label-opt` concretely, on the same three axes crc's sibling plan used:

1. **`program-v0`** — pin paper-trail's starting-point program (the dispatch-prompt bundle) that the engine plan's Phase 2c freezes and tags, resolving a branch-reconciliation problem first: the `sarol` branch's own prior optimizer design targets an older, now-superseded shape of the mainline pipeline.

**A2. Adjudicator variant — RESOLVED 2026-09-01 (Phil): the Sarol-rubric variant.** `program-v0`'s adjudicator is `experiments/sarol-2024/prompts/adjudicator-dispatch-sarol.md`, which emits **Sarol's own 9-class enum directly** (`ACCURATE`, `OVERSIMPLIFY`, `NOT_SUBSTANTIATE`, `CONTRADICT`, `MISQUOTE`, `INDIRECT`, `INDIRECT_NOT_REVIEW`, `ETIQUETTE`, `IRRELEVANT`), paired with its rubric `experiments/sarol-2024/specs/verdict_schema_sarol.md`. The mainline adjudicator + a new scorer-side collapse was considered first and **rejected** — the reasoning is recorded below because it is the load-bearing part of this decision.

**Why not mainline + a collapse: the bridge structurally loses a class.** A zero-cost cross-check (OQ2 pass 1) against `paper-tool-validation.md`'s real gold distribution — 1,873 dev+test evidence annotations, buckets verified to sum exactly: ACCURATE 1,463 / 78.1%, NOT_ACCURATE 376 / 20.1%, **IRRELEVANT 34 / 1.8%** — found that a native→Sarol-3-way collapse is **not injective**:

| Gold label | n | Sarol bucket | mainline verdict | Collapse sends it to | |
|---|---:|---|---|---|---|
| `INDIRECT` | 36 | NOT_ACCURATE | `INDIRECT_SOURCE` | NOT_ACCURATE | ok |
| `INDIRECT_NOT_REVIEW` | 17 | **IRRELEVANT** | `INDIRECT_SOURCE` | NOT_ACCURATE | **structurally unreachable** |
| `ETIQUETTE` | 16 | **IRRELEVANT** | `AMBIGUOUS` *or* `CITED_OUT_OF_CONTEXT` | excluded *or* IRRELEVANT | **ambiguous by construction** |

Mainline's single `INDIRECT_SOURCE` verdict covers two gold labels Sarol routes to *different* buckets, so 17 instances could never be predicted correctly by any program the optimizer can write, and 16 more depended on which of two verdicts the adjudicator happened to emit — capping IRRELEVANT recall at ~50% before the model does anything, while that class carries a third of a 3-way macro-F1. **The Sarol variant dissolves this entirely**: the program predicts the benchmark's own vocabulary, so every gold label is reachable and 3-way macro-F1 is directly comparable to the published baselines. (This cost was not surfaced when A2 was first put to Phil, which is why the decision was revisited.)

**The native rubric is being retired in favour of Sarol's — so nothing is traded away (Phil, 2026-09-01).** The original objection to this path was that optimizing a variant the shipped tool does not use means gains do not transfer. That objection is **withdrawn**: paper-trail's native taxonomy is itself unfounded, and the tool will adopt Sarol's 9 classes as its own rubric. Provenance, traced through git rather than inferred from missing docs:

- The **entire** native enum — all 11 sub-claim verdicts plus the rollup-only `CONFIRMED_WITH_MINOR` — appeared **fully formed in one commit**, `18b3832` (2026-04-19), the same commit that first created the verdict schema. There is no incremental derivation, no per-value history, and no design doc.
- The repo's competitor/literature review (`docs/journal/2026-04-22-lit-review-2-competitor-landscape.md`) is dated **three days later** and never discusses the taxonomy. The rubric was written *before* the field was surveyed, not derived from it.
- `paper-tool-validation.md`'s native→Sarol mapping table was retrofitted onto the existing enum afterwards, not a shared ancestry.

By contrast Sarol's 9 classes are **human-annotated over 3,063 citation instances with reported Cohen's κ** (5 annotators) and come with gold labels. Between an invented taxonomy and a validated one that has ground truth, the validated one wins — and adopting it collapses the experiment/product fork entirely: one rubric, one program, and optimizer gains land in the shipped tool.

**Consequently the severity gradation and the abstention value are removed, not preserved.** `OVERSTATED_MILD` / `OVERGENERAL` / `CONFIRMED_WITH_MINOR` (severity), `PARTIALLY_SUPPORTED`, `MISATTRIBUTED`, `CITED_OUT_OF_CONTEXT`, and `AMBIGUOUS` have no Sarol analog and no independent grounding, so they go rather than being carried as an orthogonal field. (An earlier draft argued severity was a reader-facing product feature worth keeping; that argument does not survive the provenance check, since the distinction it defended was never grounded in anything.) **But provenance answers "was it derived?", not "is it load-bearing?", and for one value the answer differs (Codex round-2).** `AMBIGUOUS` is not merely an enum member: it triggers **an entire orchestrator phase** — Phase 4 "Ambiguity triage" (`src/commands/paper-trail.md` on `main`:514), with interactive resolution keyed off `sub_claims[*].nuance` (`src/commands/ground-claim.md` on `main`:120). By the same line this plan already draws — workflow states stay, taxonomy goes — `AMBIGUOUS` arguably sits on the **workflow** side and was misclassified as taxonomy here. Severity (`OVERSTATED_MILD`/`OVERGENERAL`/`CONFIRMED_WITH_MINOR`) has no comparable machinery behind it and the provenance argument stands unmodified for those. **This does not change the optimizer decision** — the Sarol 9 remain the scored label space either way, and the adjudicator emits no `AMBIGUOUS` under `rubric_variant=sarol_2024_9class`. It changes only what the *deferred* `main` adoption should do — **resolved 2026-09-01 (Phil) in Open Questions §7: `AMBIGUOUS` is kept, as an orthogonal workflow flag outside the verdict enum, so Phase 4 survives the taxonomy retirement while the enum itself stays the Sarol 9.** **Workflow states are a different matter and stay:** `PENDING` / `NEEDS_PDF` / `STALE` / `SCHEMA_VIOLATION` are pipeline machinery, not taxonomy, and `verdict_schema_sarol.md` already treats them as orthogonal to the rubric.

**Landing is deferred — do NOT change `main` yet (Phil, 2026-09-01: "don't land on main until we're done").** Adopting Sarol natively is a shipped-tool change touching the rubric, adjudicator, extractor, `ground-claim.md`, `paper-trail.md`, `render_html_demo.py`, the README, and the committed example runs (`examples/…/ledger.md` plus both demo HTMLs carry native verdicts and would need regenerating). It gets its own scoped change against `main`, on its own merits, **after** the optimizer work here is finished. Until then the experiment continues against the variant on `sarol`, which is byte-identical in label space to where the tool is going — so no rework is created by the wait.

**Prior art this builds on.** `docs/plans/paper-tool-validation.md` (this repo, `main`) holds the already-collected label-frequency statistics used above and the named target baselines: **MultiVerS 0.59 micro / 0.52 macro F1** and **GPT-4 4-shot 0.65 / 0.45** (abstract-only variant, apples-to-apples with Sarol's own published setup). No new run is required to use either; they anchor both the OQ2 check above and the "first real scoring run" success criterion in Verification. The 9→3 collapse itself already exists in `parse_verdict.py` (`SAROL_9`, `to_3way`) and is **not** re-derived.

**⚠ The frontier scalar is 3-way MACRO-F1. Micro-F1 is a trap — do not adopt it.** For single-label multiclass, micro-P = micro-R = micro-F1 = accuracy, and ACCURATE is 78.1% of gold, so **a do-nothing program that always answers `ACCURATE` scores micro-F1 0.781** — beating both published baselines while doing nothing, and rewarding exactly the behaviour a citation-integrity tool must not have. It would be the optimizer's cheapest winning move. The same program scores macro-F1 **0.292**, which is the correct verdict on it. (An intermediate proposal during this plan's own revision did briefly adopt micro-F1; `paper-tool-validation.md`'s class-imbalance note had already argued against it. Note also that since 0.781 > 0.59, Sarol's published "micro" cannot be single-label accuracy over this distribution — it is presumably computed over the multi-label evidence structure — so micro is not a clean comparable axis either.) `score_sarol3.py --selftest` pins both numbers so this cannot be re-adopted silently.

**The output vocabulary is a fixed contract; the rubric's guidance is not (Phil, 2026-09-01).** The optimizer may edit everything that makes the rubric *good* — class definitions, boundaries, worked examples, tie-breaks, the worst-wins ordering, and all four dispatch prompts — but **not the set of emittable labels**, because the benchmark defines it and the Scorer consumes it. **That line is now physical rather than declared (OQ8, resolved 2026-09-01 — "a contract file should be immutable"):** the enum and its 3-way collapse split out into their own immutable `verdict_enum_sarol.md`, the editable guidance stays in `verdict_schema_sarol.md`, and since the engine's `contract_file` flag only checks presence, the adapter re-hashes every contract entry against the manifest after each edit pass and fails the iteration on mismatch. The optimizer prompt (Part B2) must state the 9-class enum explicitly, and the manifest records it under `output_vocabulary`. A label outside the enum is an **ordinary invalid output**: charged as a miss against its gold class and counted in `error_class_counts` — never a crash, never silently re-bucketed. A bad edit therefore just scores worse and the loop rejects it on its own, which is how every other bad edit is handled. ## Part C6 — Evidence-acquisition profiles and experiment phasing (added 2026-09-02; **revised after Codex round 3**, which found the first draft of this Part incoherent)

**Decision (Phil, 2026-09-02).** Optimize the adjudicator first, against evidence acquired **without** the agentic extractor. Bring the extractor in afterwards. The full pipeline is kept as a profile, not deleted.

⚠ **This Part is a RETROFIT SPEC, not a description of the landed code.** As of `9fc7eab` none of it exists: `adapter.py:93` defines `STAGES` globally and `:536` loops over all three unconditionally; `SarolProgramStore.editable_paths()` (`adapter.py:185`) returns every non-contract entry; and `context/playbook.md`, `prompt/optimizer-instructions.md` and `meta-learnings.md` all describe the five-file edit scope and an extractor-side INDIRECT fix. Each must be changed.

**C6.0 — The constraint that drives everything here: the adjudicator never reads the source paper.** That is a stated design invariant of the frozen prompt, not an accident — `adjudicator-dispatch-sarol.md:5` ("the adjudicator never reads the source paper. Reads only the evidence JSON and the rubric") and `:11` ("You do not re-read the source paper. You do not run new searches"). Its input is exactly `{{run_output_dir}}/ledger/evidence/{{claim_id}}.json` (`:19`).

So **"adjudicator-only" cannot mean "the adjudicator reads the paper."** Something must select evidence. The profiles below differ *only* in what does that selecting, and the verdict stage is held constant across all of them. That is the experiment: fix the judge, vary how much agency goes into acquiring evidence, and measure what the agency buys.

*(The first draft of C6 proposed reshaping `content.txt` into an envelope so the adjudicator could do its own decomposition and search. That contradicts the invariant above and is withdrawn.)*

**C6.1 — The profile ladder.** A profile fixes: what writes `ledger/evidence/<claim_id>.json`, which stages run, and which files the optimizer may edit.

| Profile | Evidence producer | LLM sessions / claim | Optimizer may edit | Status |
|---|---|---:|---|---|
| **`retrieval`** | mechanical: BM25 top-*k* over the cited paper's chunks | 1 | adjudicator prompt, rubric guidance | **Phase 1** — matches the published retrieval condition |
| **`agentic`** | the extractor subagent, then the verifier | 3 | + both extractor prompts, `verifier-dispatch.md` | **Phase 2** — the pipeline as landed today |
| **`paperclip`** | extractor querying the paper conversationally through the paperclip CLI | 3 | as `agentic`, via `extractor-dispatch-paperclip.md` | **Backlog** — see C6.10 |

⚠ **An `abstract-only` rung was proposed and dropped (Phil, 2026-09-02).** It is not constructible from what Sarol ships, and it would not have tested paper-trail anyway. `corpus.jsonl` holds *"8,515 chunks across 100 papers"* (~85 per paper) and `cited_doc_ids` is *"all chunks of the single cited paper (mean 72, median 73, max 123)"* — that is the whole paper, chunked. The per-chunk text field is *named* `abstract` only because Sarol inherited SciFact's schema; it holds that chunk's sentences, not the paper's abstract. **Note the repo contradicts itself here:** `paper-tool-validation.md:79` calls Variant A "title/abstract, match their evaluation setup", while its own line 181 says `cited_doc_ids` is every chunk of the paper — and `stage_claim.py` implements the latter. Recorded so the next reader does not rebuild the same rung. Separately, an abstract-only condition exercises none of what paper-trail is *for* (fetch, ingest, section-aware search, figures); its only purpose was a head-to-head number, and it cannot deliver one cleanly.

**The freeze does not change.** All 8 manifest entries stay frozen; `program-v0` keeps its tag and `combined_hash` `391f54fae7c5`. A profile is a consumer-side selector over stage dispatch and editable policy. The engine's materializer still sees every entry and `commit_new_version()` still stages every committed entry — nothing about the manifest is profile-aware, and no engine change is needed.

**C6.2 — The evidence envelope, stated directly.** The mechanical producers write the same file the extractor would, at `{{run_output_dir}}/ledger/evidence/{{claim_id}}.json`, conforming to the extractor half of `src/specs/verdict_schema.md`:

```json
{
  "claim_id": "C042", "schema_version": "1.1", "run_id": "run_...", "citekey": "ref_a1b2c3",
  "source_mode": "sarol_corpus",
  "handle": "pdfs/ref_a1b2c3/", "paperclip_handle": null, "ingest_mode": null,
  "claim_text": "<verbatim citing sentence>",
  "claim_type": {"type": "PARAPHRASED", "confidence": "medium"},
  "sub_claims": [
    {"sub_claim_id": "C042.a", "text": "<the citing sentence, undecomposed>",
     "evidence": [{"section": "abstract", "line": 12,
                   "snippet": "<one selected passage, verbatim>",
                   "source_mode": "sarol_corpus",
                   "locator": "pdfs/ref_a1b2c3/content.txt#L12"}],
     "figures_checked": [], "verdict": null}
  ],
  "attestation": {"phrasings_tried": ["<query 1>", "..."],
                  "section_checklist": [{"section": "content", "read": true}],
                  "indirect_attribution_check": null, "selector": "bm25-top20"},
  "stage": "grounding"
}
```

Five consequences worth stating rather than discovering during implementation:

- **`schema_version` is required, and an earlier draft of this skeleton omitted it** (found 2026-09-02 by running this very skeleton through `validate_sarol.validate_obj()`). It is in the validator's `REQUIRED_TOP_LEVEL`, and the adjudicator's output contract preserves "all other fields ... from the extractor's JSON" — so an envelope without it yields a verdict without it, and **every claim in the first Phase 1 run fails** with `MISSING_FIELD:schema_version`. Reproduced with OQ13 settled the lenient way (`"pdf"`): that was the *only* remaining violation. The producer must emit it; `"1.1"` is the value the valid fixture (`optimizer/fixtures/valid_all_sarol.json`) and the extractor prompts' schema reference both carry. Cheap to fix, invisible until a paid run, which is why it is stated here rather than left to implementation.

- **`source_mode: "sarol_corpus"` is not yet legal.** `src/specs/verdict_schema.md` constrains the field to `{paperclip, pdf, pdf_ocr_fallback}`, and that file is a **frozen `contract_file=True` entry** — so the value cannot simply be added. Either `validate_sarol.py` variant-gates `source_mode` the way it already variant-gates the verdict enum, or Phase 1 declares `"pdf"` and asserts an ingest that never happened. See Open Questions §13; this must be settled before the envelope is implemented, because the exit validator will reject every claim otherwise.

- **No sub-claim decomposition happens in Phase 1.** The mechanical producer emits exactly one sub-claim carrying the whole citing sentence. The adjudicator assigns one verdict to it and the rollup is trivially that verdict. Phase 2's extractor decomposes; Phase 1 does not. This is a real difference between the phases and must be reported as one.
- **`indirect_attribution_check` is `null` in Phase 1.** The adjudicator's rubric step 6 tells it to *use* that field. Under the mechanical profiles there is nothing to use — which is precisely why the INDIRECT remedy is out of reach in Phase 1 (C6.7).
- **The `phrasings_tried` floor needs a decision, though a smaller one than it first appeared.** `validate_sarol.py` enforces ≥3 for `DIRECT`/`PARAPHRASED`, and staging hardcodes `PARAPHRASED`. With the abstract-only rung dropped, `retrieval` is the only mechanical producer left and it *can* report its *k* queries honestly, so the floor is satisfiable rather than contradictory. **Still required:** the producer must declare `attestation.selector` (e.g. `bm25-top20`) so a reader can tell mechanical retrieval from an agentic search, and the validator should key the floor on that field rather than assume a search happened. `validate_sarol.py` is adapter-owned and not frozen, so this is a legal change; pre-filling fake phrasings to satisfy the floor is not.

**C6.3 — Comparability, corrected.** The first draft claimed Phase 1 is "directly comparable to MultiVerS 0.52 / GPT-4 4-shot 0.45" while feeding the adjudicator all ~72 chunks of the cited paper. That is wrong, and this repo already documented the right answer: `paper-tool-validation.md:79` defines the apples-to-apples variant as *"feed paper-trail only the citing sentence + cited paper's title/abstract. Match their evaluation setup."* Sarol's own MultiVerS result used BM25 + MonoT5 top-20 retrieved sentences, and their GPT baselines used top-5 for cost.

| Condition | Comparable to the published baselines? |
|---|---|
| `retrieval` at *k*=20 | **Yes, to MultiVerS** — same retrieval budget; report *k* alongside the number. The only comparable condition the ladder offers |
| all-chunks (the withdrawn first draft) | **No** — a different evidence budget entirely |
| `agentic` / `paperclip` | **No** — these are the full-paper wedge (Variant A′); report as Δ over Phase 1, never head-to-head |

Any Phase 1 number must be reported with its evidence condition attached. A macro-F1 without the *k* is not a result.

**C6.4 — What each phase claims.** Phase 1 establishes how well the frozen judge performs at a *fixed, mechanical* evidence budget, on the same footing as the published baselines. Phase 2 replaces the mechanical selector with the agentic extractor and measures the delta against Phase 1's *optimized* adjudicator.

That delta is the paper's actual claim — **does agentic evidence acquisition beat retrieval?** — and it is measurable only because the judge is held constant and Phase 1 runs first. Optimizing both at once would confound them.

⚠ **A bias note that must accompany any Phase 1 → Phase 2 comparison.** The two conditions differ on more than agency: Phase 1 hands over a fixed top-*k* with no decomposition and a null `indirect_attribution_check`; Phase 2 decomposes into sub-claims and populates that field. A Phase 2 win is therefore not attributable to agency alone. Either hold decomposition constant or report it as a confound.

**C6.5 — A profile is part of a run's identity.** Macro-F1 under two profiles measures two different systems, and the engine's frontier is a bare scalar — `_select_best` and `_regressed` compare numbers with no idea where they came from. Enforcement is entirely consumer-side:

- the profile is written into `run_manifest.json`, and into `release_train.json` / `release_val.json` as a key inside the adapter-owned `corpus` / `breakdown` payloads (`ReleasePayloadTrain`/`ReleasePayloadVal` are engine dataclasses with no profile field and must not be changed);
- the profile is passed as `run_loop(hard_fields={"profile": ...})`, so `engine.resume` STOPs a resume whose recorded profile differs;
- `schema_version` bumps `0.1.0` → `0.2.0` when the profile key is added.

**C6.6 — Cost.** Per iteration at TRAIN=10, VAL=316 (the engine calls the Runner three times — TRAIN, VAL, post-commit probe — so 642 claims):

| Profile | Sessions / iteration | ≈ $ / iteration |
|---|---:|---:|
| `retrieval` | 642 | ~$32 |
| `agentic` / `paperclip` | 1,926 | ~$96 |
| `retrieval` + probe cache | 326 | ~$16 |

`CostModel` must take the profile and derive `stages_per_claim` from it rather than hard-coding 3. The canary, when configured, runs once per `SarolRunner.run()` call — three per iteration — so it adds `3 × stages_per_claim` sessions and must be a term in the model, not an untracked extra.

**C6.7 — What Phase 1 deliberately cannot test.** The named remedy for the INDIRECT blind spot (`experiment-april-20-findings.md`) is extractor-side: promote `attestation.indirect_attribution_check` from a free-form note into a structured field the adjudicator must consume. Under the mechanical profiles that field is `null` (C6.2), so the fix is unreachable and the hypothesis narrows to *can the adjudicator detect indirect attribution from the passages it is handed?*

`meta-learnings.md` (P1), `context/playbook.md` and `prompt/optimizer-instructions.md` must be updated **in the same change that lands the profile**, not before — today they correctly describe the landed full-pipeline behaviour, and changing them early would make docs and code disagree.

**C6.8 — Mistake corpus: per-claim, not counts.** Part C2 specifies per-claim adjudicator reasoning plus evidence, TRAIN-side fully open. The landed implementation returns only `MistakeCorpus(ref=<run manifest path>, counts=error_class_counts)` (`adapter.py:825-835`), so the optimizer sees aggregate error classes but never which claims failed, what it answered, or what gold said. On a Tier-1-open split that is close to scalar-only optimization. **This is a repair of a wrong implementation, not a check to add.**

Required, concretely: the Scorer already computes the prediction/gold join and discards it. It must persist it to `<train_output_root>/mistakes/<batch_id>.json` as a list of `{claim_id, citekey, claim_text, evidence_snippets, pred_label, gold_label, pred_3way, gold_3way, adjudicator_reasoning}`, and `build_mistake_corpus()` must point `corpus.ref` at **that** file rather than at the batch run manifest. `MistakeCorpus` exposes only `ref` and `counts`, so the richer content rides behind `ref` — no engine schema change.

**Three actors, not two** — stated because an earlier draft of this work conflated the first two:

| Actor | TRAIN gold | VAL gold | TEST gold |
|---|---|---|---|
| the program (nested sessions) | never | never | never |
| **the optimizer** | **fully open** | scalar only | sealed |
| the scorer (`parse_verdict.py`, code, not an agent) | reads | reads | reads once at unseal |

Rule 1 sandboxes the *subagents*. The optimizer reading TRAIN gold is the mechanism by which it learns, not a leak.

**C6.9 — VAL outputs and the optimizer's read scope (corrected diagnosis).** An earlier draft claimed TRAIN and VAL per-example outputs share one root separated only by a subdirectory name. **That is false.** `RunInputs.batch_id` is `f"{run_id}-train"` / `f"{run_id}-val"` (`dispatcher.py:474,477`) and the Runner defaults to `materialized_path.parent / f"runs-{batch_id}" / split` (`adapter.py:514-515`), so the two roots already differ unless a shared `output_root` is injected.

The real requirement is narrower and still unmet: **the VAL root must lie outside the optimizer's readable mounts.** Specify `train_output_root` and `val_output_root` explicitly rather than relying on the derived default, grant the optimizer only the TRAIN corpus ref and the release files, and add a negative control that attempts to read the *concrete* VAL run-manifest path the selected runtime actually uses — not a generic `val/` directory.

**C6.10 — `paperclip` profile (backlog; Phil, 2026-09-02).** A fourth rung on the ladder: rather than being handed passages, the extractor *queries* the cited paper conversationally through the paperclip CLI, using the already-frozen `src/prompts/extractor-dispatch-paperclip.md` path — so no new prompt enters the manifest.

Why it deserves its own rung rather than being a variant of `agentic`: it separates *what evidence is available* from *how the agent goes and gets it*. `agentic` reads a staged flat file; `paperclip` issues repeated targeted queries against an indexed document and can follow up on what it finds. If the Phase 1 → Phase 2 delta turns out small, this is the natural next hypothesis for where agency actually pays.

Blocked on a prerequisite the other profiles do not have: the Sarol cited papers must first be ingested into a paperclip corpus, and the `paperclip_cli` pin (`0.5.11`) already in `runtime_pins` becomes load-bearing at run time rather than merely recorded. Not scoped here; recorded so the ladder is visible as a whole.
