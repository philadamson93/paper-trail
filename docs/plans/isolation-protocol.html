In short

Today the session being judged can see the whole repository, including the answer key. This work replaces that trust with a wall: the judging session runs inside a container that has been handed only the few folders it needs, so the answers are unreachable because they were never mounted — and a decoy planted in the answer folder proves it, because the session must fail to read it. The point is that the optimizer is allowed to rewrite the instructions but cannot rewrite what was mounted.

What changed since you last looked: the general machinery moved out of this plan into the shared engine and landed there on 2026-09-17. The contract, in one table new

This is the whole interface between the two repos. The engine owns the left column; paper-trail owns the right.

Grant fieldWhat the engine does with itWhat paper-trail puts there
programMounts it read-only and makes it the working directory The frozen program snapshot, addressed by version
readableMounts each pair read-only The materialised spec root
writableMounts each pair writable The claim staging root — not one claim — and a trace directory
workdirSets the container's working directory, and refuses a bad one The snapshot path
deniedRenders nothing. It exists to be probed — and a grant with an empty denied is refused outright, because it is a grant with no proof The answer key, the held-out set, iter/, the optimizer's findings and notes

Why denied is the load-bearing field, and the one we would be tempted to leave empty. Mounts only ever grant. A folder that was not mounted is already unreachable, so writing it into a deny list changes nothing about what runs. Its entire job is proof: every entry gets a decoy planted in it, and the check is that the session fails to read the decoy. The engine refuses an empty list rather than letting a proof-free grant through.

SessionScope(

    writable = ((staging_root, "/workspace/staging"),
                (trace_dir,    "/workspace/trace")),
    workdir  = "/workspace/snapshot",
    denied   = (gold_dir, benchmarks_dir, iter_dir, findings_dir, meta_learnings),

The steps

Read first — what the engine landed, and what this plan deletes new
Entirely new this round. It is the only section that describes the current division of work, and four of this plan's twelve build items are answered by it.

The engine's plan is Completed, merged at 592862f, with 367 tests passing and none skipped — every live container probe actually ran — and 34 of 34 deliberately broken variants caught. Four things this plan specified are now upstream:

  • Our mount vocabulary becomes the engine's SessionScope. It renders no Docker flags of its own, which is what stops it being a second, competing way to say the same thing.
  • Our host-path check becomes host_path_leak — and it is strictly better, because it takes the grant and can therefore tell a leaked path from one we granted on purpose.
  • Our per-dispatch container factory becomes render_dispatch: one standing network, a fresh container each time, each grant's command provably distinct from the next.
  • The generic half of the decoy test becomes negative_control.py.

Why it moved. Your words, 2026-09-15: most of this should go in agentic-label-opt, not build to lift later. There is a longer version of this story in the engine plan — a ruling you made on 2026-07-20 said build it as a general capability, the ruling got written down in a third repo and never reached the engine, and this plan then spent two months building it consumer-side under a "change nothing upstream" goal.

Two things that were blocking are now cleared new
New. Last time both of these were open, and one of them meant Phase 1 literally could not run.
  1. Passing the API credential. The renderer could only write a secret into the command itself, and the wrapper records the full command to a file — so the honest position was that the rendered command carried no authentication at all and nothing could run. The engine now passes a credential by name, and refuses a name-equals-value string rather than quietly letting it through. Still true the token is visible inside the session; hiding it from there needs a broker and is out of scope.
  2. The egress shape. You asked what the "open" setting was for. It seals nothing — the engine files it under unrestricted policies, and it was built for a different consumer. The alternative, a one-host allowlist, had a shape problem: it fixed its command up front but only stood the network up on entry, so one network could serve exactly one container. A loop that dispatches per claim cannot use that. Those two moments are now separate, so the one-host allowlist is reachable.
Your two corrections came out free new
New, and the most useful thing on this page. Both corrections were booked as code we still owed; adopting the engine's design applies them by itself. ⚠ Updated 2026-09-17 after Phil struck this page's first reading of the per-stage question — see the callout below.

A rule the code could drift away from has become a shape the code cannot express, which is the better outcome:

  • The per-stage split is gone, entirely. Stages are a pipeline convenience; the boundary that matters is that the program cannot reach the answers. The engine's grant has no stage dimension at all, so adopting it drops the split rather than us remembering to.
  • The grant covers a worker's whole life, and N is a parameter. Mount the staging root, not one claim, and check uniqueness per grant rather than per claim.

Your ruling of 2026-09-17, which corrected this page's first draft. An earlier version of this card said the extraction step would get "its own grant" once it is dispatched for real. That is the same per-stage boundary, just postponed — and you struck it:

We've decided several times now that the entire program is one entity in terms of data visibility. While there are "stages" nominally, nothing experimentally warrants or benefits from splitting in this way. In fact the optimizer may freely choose to edit the topology of a program making such divides a nuisance and unnecessary.

So: one grant for the program, whatever stages it runs. A wider program means a wider single grant, never a grant per stage.

It also settles a contradiction the plan was already carrying. The plan conceded that keeping the paper away from the judging step is about measurement integrity, not leakage — and its own rule sends that class to Plan A and its gate, not here. Then it kept the per-stage split anyway. What actually holds the evidence condition steady is the release pinning the profile and the retrieval depth, which the plan says itself. The mount set was never the mechanism.

And one that is invisible today. At one question per worker, the right rule and the wrong rule look identical — so a wrong check here passes now and starts mis-attributing results the moment we ask a worker more than one question.

1a — pin which version of the engine we run against changed
Now names the actual target, 592862f, and records that the pin will genuinely work — which was worth checking, because the reverse would have sunk the item.

The problem. paper-trail depends on the engine at runtime — our dispatcher drives its loop, our adapter implements its four interfaces — but has no packaging file of any kind. It finds the engine by pointing at a folder in the home directory, in three separate places. So a run binds to whatever happens to be sitting in that folder at that moment: whichever branch is checked out, including uncommitted edits. The bytes under test are unrecorded and the run is not reproducible. That is this plan's own root cause in miniature.

The fix. Copy what rad-eval already does: pin a git revision in a packaging file. Target is 592862f. This creates paper-trail's first pyproject.toml, so it is more work than adding a line to an existing file.

Checked, because the item would be unbuildable otherwise. A pin only helps if the installed package actually exposes what we import. The engine's packaging includes both of the pieces we need, so importing them from the installed package works — it does not only work from a folder path. Packaging that exports one module and quietly omits the others is a common way for exactly this to fail.

Files: new pyproject.toml; the three hardcoded paths become development-only.

1b — fill one grant for the judging session changed
Rewritten. It used to build a per-stage mount set with its own vocabulary; it now fills one of the engine's grants.

Grant: the claim staging root writable, the spec root read-only, the version-addressed snapshot read-only and as the working directory, a trace directory writable. Everything else — iter/, the optimizer's findings, its notes, the answer key, the held-out set — goes in the denied list: unreachable because unmounted, and probed by the decoy test.

1c–1g — the container, the trace, the refusal, the decoy
  • 1c, one container per dispatch. The prefix cannot be built once at start-up: the snapshot changes per program version, staging and trace per claim. Comes from render_dispatch.
  • 1d, keep the trace. Containerising throws away the judge's session transcript, because the code that finds transcripts looks in the host's home directory and goes blind inside a container. Write the streamed session JSON beside the verdict.
  • 1e, the optimizer's own container. Modelled on rad-eval's, which has been run for real. The scorer, the answer key, iter/ and the manifest are absent from its mount set, so "the optimizer cannot edit the scorer" holds by construction rather than by instruction.
  • 1f, one place that refuses an unboxed run. The census is 22 construction sites — of which only 3 actually ship; the other 19 are tests. It must cover three ways in, including one that skips the usual door. Tests opt out by injecting a fake container prefix, never a boolean.
  • 1g, the decoy. Decoys planted in the answer key, the held-out tree, iter/ and the optimizer's findings. The session must fail to read each — and the test has a control of its own that must fail, so that a pass means something.
Phases 2–4 — layers inside the box, record the shape, reset at run start
  • Phase 2. Narrower layers behind the wall, including staging the held-out set per iteration so the live verdict file is provably absent before a dispatch.
  • Phase 3. Record the exact rendered shape — image digest, every mount with its role, network policy, allowed hosts, session flags — into the manifest, read from the committed version rather than the working copy.
  • Phase 4. Archive the optimizer's notes and findings at run start and assert they are gone. Not a fresh clone per run; you ruled that out.

Gotchas

A safety number in the record is zero for a boring reason

The armed run from 2026-08-05 reports zero denials. That is zero by construction — container mode has no hooks to do any denying. It must never be cited as evidence the boundary works.

Four container paths are reserved, even when nothing is mounted there

The engine reserves a handful of paths under its workspace and refuses any mount that collides with, nests under, or sits above one — and it reserves them even when it mounts nothing there, which is our case. The plan originally named one of those paths for the snapshot, so as written it could not have run. The free dry run caught it on its first execution, which is the cheapest bug this plan has found.

This plan once cited a file 23 times that was not on the machine

The findings document behind this plan lives in a folder that is deliberately kept out of git, so it never travelled — and for most of this plan's life it was not on the authoring machine at all, while the plan cited it 23 times and keyed seven steps to its item numbers. Every one of those citations was unverifiable. The fix was not a better citation: the nine-item list those steps derive from is now reproduced in the plan itself.

The word "judge" was swept out of this plan on purpose

108 of 142 uses were rewritten — to the program where the text meant the container, the mount set or the read boundary, and to the adjudicator where it meant the step doing the judging. The 34 that remain are deliberate; don't "finish" them. It was not cosmetic: "the judge's mount set" reads as one mount set, where "the program's" raises the question of which step — the difference between a correct boundary and a gap.

The product is not half-built, whatever the harness says

paper-trail the product runs all three pipeline stages end to end and has for months. What is narrow is the measurement harness, which dispatches the judging step alone so the measurement isolates it. Two flags in the code describe the harness, never the product. This was mis-stated twice, so it is worth keeping straight.

Two claims the engine plan flags as NOT verified new
Carried over from the engine's own confidence table, because one of them originated as a paper-trail citation that resolves to nothing.
  • Docker refusing a writable mount nested inside a read-only one. This plan cited rad-eval's deviation note for it; the citation resolves to nothing. The engine settled it against a real daemon before landing.
  • Whether the network sidecar costs once per run or once per dispatch. Inferred, not measured — and the whole recommendation to move off the unrestricted setting rests on it.
