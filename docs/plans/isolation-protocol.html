What this is for

Every number the optimizer has ever seen came from a judge session that was running with the whole repository as its working directory, with permissions switched off. That tree contains the optimizer's own notes on which claims it got wrong, its running list of hypotheses, and a file of per-claim gold labels. Across 561 judge sessions, none of them read any of it. But thirteen lost their task and fell back on looking around, and two of those listed the optimizer's own notes as candidate work. The only thing between "listed" and "opened" was that nobody was there to say yes.

So: put the judge in a container where those files are simply not present, put the optimizer in one where the scoring code is simply not writable, and prove it with the test whose absence caused all of this — plant a marker file where the gold labels live and show a judge cannot open it.

The shape of it, in your terms

Two things fixed, one thing free:

  • Scoring is deterministic code we never touch. The scorer makes zero model calls, and exactly one file is allowed to touch gold.
  • How the agent produces a label for an example is 100% the agent's choice — the prompt, the rubric, the judging instructions, the shape of it, and whether it writes Python to do the job.
  • The only bound on that freedom is no leakage and no cheating, and that bound is enforced structurally, by what is and is not in the container — not by prose rules the agent could edit away.

So there are two boundaries:

BoundaryWhat it stopsWho builds it
Read — the judge cannot reach gold, the optimizer's workspace, or the benchmark dataleakagethis plan, our side, no engine change
Write — the optimizer cannot edit the scorercheatingCorrected this round: also ours, not the engine's. The engine part the plan said was missing is already done and tested; our side is not started.

Everything else is a layer behind the read boundary, or an integrity fix that has to land before any number means anything.

Why this happened, and the shape it keeps taking

The requirement existed verbatim in three places: an attack table naming "optimizer workspace not in subagent scope", a hygiene rule saying violations invalidate the verdict, and a canonical invocation recipe. None of the recipe shipped — zero of its five settings appear anywhere in the code.

It was traded for making things work. One setting needed the judge to have a real checkout, so the code kept one — and "a real checkout" was silently read as "the whole repository" in the very first commit, with no plan line recording it. Then a requirements doc claimed a guarantee stronger than our peers' on the grounds that there was nothing in the repo to deny access to — true of gold, false of the training results the loop writes back into the repo. Across ten review documents, every isolation finding points the same direction: reviews audited the direction that had a test, and never the direction that had only prose.

The tighter statement, and the one to act on: in every single instance, a mechanism that would have covered it already existed and was pointed somewhere else. The frozen manifest existed and omitted the judging instructions. A gate existed and was scoped to the wrong read path. Code asserted a reset lifecycle that nothing implemented. A pinning mechanism existed and pinned a tool the only working setup never invokes. That matters because it says re-aim what exists, not build another one.

Every phase in this plan is that shape, which is why it is smaller than it looks. And it is why the review's findings land where they do: four of the review's findings are that same pattern, one level up — the probe list, the constructor set, the fingerprint, the file count. None was wrong. All were pointed slightly elsewhere.

The phases

Phase 0 — the integrity floor ● OQ5 resolved

What changed this round: you resolved OQ5 — a broken dispatch fails loudly and the optimizer fixes it, no retry. The three scoring-around options are gone.

Three fixes that are independent of the containers, and nothing downstream is measurable until they land.

Archive the previous answer, then check it is gone. Today a re-dispatch overwrites the old verdict. Move it aside first, then assert the live path is empty. This also preserves the prior answer instead of destroying it.

Refuse to score a dispatch that produced no answer. This is the load-bearing one, because you ruled the delivery text stays editable — nothing prevents a broken dispatch, so this is the only thing between one and a poisoned iteration. A naive fix zeroes the whole batch: the scorer demands every claim be accounted for, so a new third outcome drops the claim and returns 0.0 for all fifty. That is exactly the failure of 7 September, where 93 of 100 claims were fine and every number came back 0.0.

OQ5 resolved this round — allow it to fail. No retry. A dispatch that produces no verdict fails the claim, and that failure is handed to the optimizer as feedback: the delivery path is the optimizer's to edit, so a no-task dispatch is a defect it owns and should repair, and a silent retry would hide exactly the defect it is meant to see. The refuse-to-score gate still stands (never read the stale answer, never score the batch 0.0); the failure is recorded under a distinguishable count and never reported as program quality. Dropping the retry also removes the result-cache trap, the count desync, and any tension with the consistency gate.

Render the dispatch prompt in code — as a default the program may override. Both observed delivery bugs appear nowhere in the repo; the model wrote them at run time, differently each time, and 13 of 561 sessions started with no task at all. Code fills the placeholders. Per your ruling this is a default, not a constraint: what reaches the subagent is 100% program-authored either way.

Phase 1 — the containers, the boundary itself

What changed: this is where five of the six criticals landed. Three steps became seven, and both principals now get a container.

1a — depend on the shared engine. We have no dependency on it today: two mentions in prose, no package. Nothing in this plan can be built until that exists. Pin it to a specific commit, not a branch — pinning to a branch is what let a six-week-stale document outrank live code in the first draft.

1b — the judge's mounts, plus two things mounts do not cover. The mount set itself needs no engine change; the renderer is already generic enough. But the login token gets written into the command line and into a log file, and a token is our documented login path — so passing it by name is a prerequisite, not a follow-up. It fixes the command line and the log; the token stays readable inside the session, which needs a credential broker and is out of scope. And the tool list is a named deliverable, not a flag choice, because it covers the four threats a mount cannot touch: what commands run, outbound network, the credential, and what a subagent inherits. The list must include the subagent tool — the judge is one, so leaving it out kills every dispatch while looking like a tightening.

1c — build the container command per dispatch. The first draft built it once at startup and that cannot work: the program version changes per iteration, the scratch space per claim, and the staged command currently has real machine paths baked into it that mean nothing inside a container. So one command per dispatch, built from a single map of machine path to container path, and every path translated through it — the arguments, the extra directories, the working folder, and any path written into the prompt text. A path that is right in the arguments and stale in the prompt is a dispatch the judge cannot finish, and it will look like the model failing.

1d — keep the transcript. Transcript lookup searches the machine's own folder, which inside a container is the container's, thrown away when it exits. So containerizing silently ends traceability — and traceability is how the contamination was found at all. The cheap fix needs no new plumbing: the session text is already held in memory, so write it out beside the verdict.

1e — the optimizer's container. Your ruling. Model it on the one rad‑eval already runs: 198 lines, on main, a real armed run behind it. What it buys over a permission rule: the scorer, gold, and the manifest are simply not in the optimizer's mounts, so "the optimizer cannot edit the scorer" holds by construction. One caution — a literal copy does not give us the write boundary, because rad‑eval's setup hands the whole clone to the sandbox account with editing still allowed. Take the mounts, drop that part.

1f — one place that refuses to run uncontained, covering every case. There are 21 places a judge gets built, not the 7 the first draft counted — 19 in one file, one in the canary, one in the baseline script. A check in the shared setup path protects the cases that go through it and silently does not apply to the rest, which is worse than failing. So the refusal moves into the constructor, and the count itself gets asserted. No exemption for anything that produces or guards a reported number — the baseline script produces Plan A's fresh baseline and the canary guards it. An exemption there would mean the baseline is measured on the uncontained instrument while everything compared against it is measured on the contained one. That is not a weaker guarantee, it is an invalid comparison.

1g — the sentinel test. Plant markers, prove a judge cannot read them. Markers include gold and the benchmark data, which the first draft left out entirely — they are the highest-value secrets in the system.

Also recorded: containerizing swaps the instrument. The image pins an older CLI than the one installed, 49 patch releases apart, at the exact moment this plan owes Plan A a clean baseline — so pinning the image to the installed version is an explicit deliverable and a gate checks it. And container mode writes zero audit rows, so four of the engine's automatic tripwires go blind. Recorded as a decision, not a surprise.

Phases 2, 3 and 4 — the layers behind the boundary ● OQ8 resolved

What changed: the working folder is now tied to the program version (a critical), the configuration fingerprint covers the container (it covered nothing about it before), and the per-run clone finally has a build surface — or gets split out, which is OQ9.

Phase 2 — narrow what the judge sees. Phase 1 makes things unreachable; Phase 2 reduces what is exposed even where the mounts already deny it. It removes the look-around channel that actually fired in September's run — which turned out to be git state, not project context. The sessions enumerated filenames "based on the git status", and a working folder with no git history kills that at the source.

The critical here: a single fixed working folder cannot serve the now-editable judging instructions. Their bytes differ per program version, so one shared folder serves whichever version wrote it last — and a v0 dispatch and a v1 dispatch in the same run could execute the same instructions while the results say they ran different programs. Plausible verdicts both times, and nothing downstream would show it. So the working folder is addressed by version, and the cleanest form is already on disk: the per-iteration frozen snapshot already contains the instructions at the same path, is already read-only, and has no git history in it. The one unknown is whether the tool can run with a read-only folder; the cheap probe settles it, and either way the version-addressing requirement stands.

Phase 3 — pin the configuration. There is a field for this already and nothing ever computed it — this run wrote a literal string into all ten payloads. The pin goes in the committed manifest, not a new file, because a guard whose reference value is not under version control is not a guard.

What the reviewer caught: the first draft's fingerprint covered five things and every one was about the machine, not the container — so swapping the container underneath it would leave the fingerprint unmoved, and the pin would certify a setup it never saw. It now covers the image digest (a version string is not a digest; the same tag rebuilt on a newer base layer is a different container), every mount with its role, the network policy, the container user, the working folder, the permission mode, and the tool list. Two rules on top: names not values for environment variables, so rotating the token does not read as a configuration change and get the gate switched off; and the mount set as rendered, so the fingerprint is computed from the same bytes the seal test probes.

Phase 4 — one clone per run. The finding from Plan A: the optimizer's lessons sheet is injected into every session and has never been reset between runs, while the code reasons as though a reset were guaranteed. So two runs both labelled the same version could open with different inherited hypotheses and nothing would record it. A fresh clone per run closes it, retires a gate built to work around it, and removes most of the danger from the baseline recut.

OQ8 resolved this round — local git and local disk. paper-trail is not PHI and never will be, so the clone and its archives stay on local VM disk; plain git is a fine home and no bucket is needed. The shared-mount "bucket mode" — run state landing on the mount so a PHI consumer can keep it off local disk — is a capability for a repo like crc, which paper-trail leaves off. This also sidesteps the mount's slow small-file reads.

OQ9, and it is a real scope question. The reviewer's judgement was blunt: Phase 4 as written is not buildable by a fresh session — it named a helper and left out who makes the clone, what happens on resume, the version-tag policy, and every place that assumes the old repository root. It now has that surface written out. But it is still the largest remaining unknown in a plan that already covers two container boundaries, so the question is whether it stays or becomes its own reviewed plan. Splitting has a real cost: the optimizer's mounts are defined against the clone, so a split means its boundary is weaker until the clone follows.

What we found on disk that changed the design

Nine findings, all verified against the code, kept only where they still steer a decision.

  • The hook-based safety net does not exist anywhere. No settings file, no per-action check in the judge's path at all — so the trade that bought the wide working directory bought nothing. It also quietly retires a control the tracking doc says should be committed, which is OQ6: retiring it is defensible now the container supersedes it, but it has to be on the record, because reasoning a requirement away in passing is this plan's own root cause.
  • The held-out path has no iteration number, by design in the engine. That is why the stale-answer fix archives by timestamp instead of by iteration.
  • The archive fix has to land before the fail-closed fix, not beside it. While a stale answer can be read, refusing to score a missing one changes nothing.
  • The judge side needs no engine change. The interface is duck-typed and the mount parameters are already generic enough.
  • The old recipe cannot be restored as written. Its last step grants the judge exactly what this plan is removing. So the pieces get adopted individually with that one inverted.
  • The judge inherits the optimizer's entire environment, including the variable that points at gold. Nothing filters it today.
  • The judging instructions are optimizer-editable and stay fully so (your ruling). This is load-bearing in both directions: it is why the broken-dispatch check is the floor of Phase 0, and it is why two of this round's criticals exist — a per-version editable file cannot be served by one shared copy.
  • The evidence envelope is not version-covered. The manifest's ten entries are all markdown, so the code paths are unversioned. Plan A owns that.
  • Gates run once at preflight while the optimizer edits mid-run. Real, but you were right that it is not isolation — it is measurement integrity, and it belongs to Plan A. Sorting all eight prohibitions by that test is what removed a whole step and a whole gate from this plan.
What gets touched ● OQ4 reframed

What changed this round: OQ4 reframed the shared-engine line — much of this belongs upstream because crc needs it too, so it is a modularity call, not an ownership one.

Two new modules of ours — one for the isolation concern (the scope check, both mount sets, the machine-to-container path map, the environment allowlist, the version-addressed working folder, the configuration fingerprint), one for rendering the dispatch prompt. Plus a third if the per-run clone stays in this plan (OQ9), which would own the provisioning the shared helper does not do.

A dependency we do not have. There is no package dependency on the shared engine at all today — two mentions in prose. That has to exist first.

The judge adapter is the biggest surface, and bigger than the first draft said: the per-dispatch command factory, the refusal in the constructor covering 19 sites in that file alone, path translation everywhere a machine path crosses the boundary, writing the transcript out, and the scoring changes whose lockstep readers turned out to be seven places rather than three.

The shared engine: four files, not one. The first draft claimed one and that was wrong even on its own terms. Passing the token by name is a real change. A new test control needs matching assertions in the test file. Re-pinning the image's tool version touches the image definition and its README — and that README is the file whose six-week-stale sentence outranked live code in the first draft, so correcting it is part of the change, not tidying. Still nothing in the engine's core loop.

OQ4 this round — the dividing line is modularity, not ownership. Do not treat these as paper-trail's problems alone: crc-extraction-agent needs much of the same — the container boundary, the by-name token transport, the audit rows, the isolation-label check, bucket mode — and both repos are ours. So the test for each piece is where it should live: it goes upstream when a second consumer needs it, and stays here only when it is genuinely paper-trail-specific (its own sentinels, which paths its own gold sits behind). Only the mount contents are ours; the machinery is shared.

Deliberately out of scope

Named so they read as decisions, not oversights: a corpus counting bug; the runner printing a lagging metric; the evidence envelope and the post-edit checks, which are Plan A's; one line owed to the optimizer's own instructions (once containers land, tell it that gold and the wider repo are denied, so telling the program to read them just wastes an iteration — guidance for efficiency, not a gate); letting the optimizer write Python, which the boundary already permits — the real constraint is that the freeze step lists files by hand and has already crashed on exactly this; and the measurement redesign.

How we'll know it worked

What changed: seven new gates, and the two biggest existing ones were rewritten because they could pass on a broken system.

The rule that keeps catching things. A test that reads a value out of something it does not write has to assert the value is there, not just compare it — comparing against a missing or empty value passes and reports green while checking nothing. This round the rule caught four holes, two of them in this plan's own centrepiece.

The centrepiece, rewritten. The sentinel test used to probe a list of paths. That only shows those paths are absent — it says nothing about the whole repo being mounted somewhere unexpected, where every probe still fails while everything is readable one directory over. The test was aimed at the paths we thought of, which is the same defect as every other finding in this plan. It now asserts the exact set of mounts first, rejects any mount that contains a forbidden path, probes every mount it finds in the command rather than every path we remembered, and adds a control that must fail — mount the repo somewhere unexpected and the test has to catch it. Without that control, the exact-set assertion is itself untested.
