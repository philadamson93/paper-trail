What changed since you last looked ● 13 findings applied

An independent cross-model review (Codex, its second pass on this plan) read the plan against the live code in all three repos. Thirteen findings applied, none disputed. Its verdict was Blocked — not because the design is wrong, but because three things in the document would have sent an implementer down the wrong path.

The three that matter, and all three were corrections to claims I had made:

  1. The permission-bypass flag is set in two places, not one. I had written that it wasn't ours to change. Wrong: we pass it ourselves for the program, and the shared engine passes it for the optimizer. So the program's fix is a local edit available now, not something waiting on upstream — and an implementer who only changed upstream would have left the program running wide open while the diff looked like a fix.
  2. The gold labels are one hop further away than the plan said, and that moves the test. The release file carries a pointer; the answer key is the file it points at. A sentinel planted in the release would have passed while the program could still follow the pointer and read the answers. See the chain below.
  3. Old wiring was still in the test list. After you cut the middleman session, two gates still demanded the middleman-plus-subagent shape and required the subagent tool to be available. They now assert the opposite.

Two genuinely new: pinning the engine in a package file changes nothing unless the import path changes too (today it reaches into a hardcoded folder in your home directory, in two separate files) — and a free dry run is now the first gate: render every command for every stage and profile, start no container, call no model, and assert no host paths leak in and no two dispatches share a command. Cheapest check in the plan, covering the two defects most likely to survive review.

Three new live questions came out of it, listed in the questions panel: whether this build covers all three pipeline stages or just the judging one (this one blocks starting), whether the old environment-variable override survives the pin, and how program versions get identified.

Baseline: the plan as this page showed it before that review. ⚠ The previous file's metadata claimed an older version than its own content, so a naive diff would have re-shown you nine rounds of edits you have already reviewed and responded to. This is one round's delta.

What this is for

Every number this project has produced came from a judging session that could see the whole repository, with permissions switched off. In that tree sit the optimizer's own notes on which claims it got wrong, its running list of hypotheses, and a file that leads to the answer key.

Across 561 judging sessions in the September run, nothing was actually read. But 13 sessions that lost their task fell back on looking around their working directory, and two of them listed the optimizer's own findings as candidate work — for a claim they were in the middle of judging. The only thing between "listed them" and "read them" was that no human was there to say yes.

So: make the boundary a fact about the filesystem instead of an instruction in a prompt the optimizer is allowed to rewrite. Then prove it the way nobody has yet — plant a marker file where the answers live and show a judging session cannot open it.

Who is who — the two things that get a box

This matters more than it looks, and getting the names wrong already bent the design once.

The agentic programThe optimizer

runsevery stage × every claim. Today 1 × 561; with the full pipeline 3 × 561once per round — about 5 times in a run
never readsgold labels, the benchmark data, the optimizer's findings and hypotheses—
never writes—the scorer, gold, the releases folder, the manifest — it would be marking its own homework
in a box❌ no. This plan adds it. Nobody has built one, anywhere✅ built and really run — in rad-eval; ❌ not here

Where "the judge" fits. The program has three stages: one finds the evidence, one judges the claim, one spot-checks. The profile running today uses only the judging stage, which is why the judge and the program have looked like the same thing. They are not — the full pipeline runs three sessions per claim and the judge is one of them. So "judge" is fine as the role of the judging stage, but naming the box after it freezes in a temporary accident.

Three things that name was hiding, all design changes:
  • The box is per stage, not per claim. The dispatch loop already runs once per stage. A command built per claim hands all three stages the same one.
  • Each stage needs different mounts — and only the judging stage's was worked out. The evidence-finding stage has to read the paper; the judging stage should get only the finished evidence. Invisible today because the evidence is prepared by plain Python before any session starts.
  • The cost triples with the full pipeline. Measure per stage, not per claim.

⚠ Neither of them is the scorer. The scorer is plain Python that makes no model calls at all — it compares answers against gold and sits outside both boxes. It is never an agent. Where this plan talks about protecting "the scorer", it means that code and the gold it reads.

⚠ Known debt: the plan's own title and about 120 of its sentences still say "judge" where they mean the judging stage. The definitions here govern. Sweeping the document is a blocker before implementation, not a tidy-up, because the two readings differ exactly where it matters — one mount set, or three.

The work, phase by phase

Numbered in build order. The boxes come before the layers behind them. Nothing here is implemented yet — the plan is still a draft.

Phase 0 — the integrity floor pending

Nothing downstream is measurable until this lands, and it is independent of the boxes.

0a — give the held-out set a round number, then check the slot is empty. Today the training side gets per-round inputs and the held-out side does not: the same object is reused every round, so round 5's judge runs in round 1's folder on top of round 1's answer. Proven on disk: two rounds point the same claim at the identical directory, and one answer file is timestamped four hours after the folder that contains it. That is the 61% contamination. The fix is a two-line widening upstream, mirroring what the training side already accepts — plus a check that the answer slot is empty before each dispatch, which is what makes "refuse to score" mean anything.

0b — refuse to score a dispatch that produced no answer. This is the load-bearing step, because the delivery path stays editable: nothing prevents a broken dispatch, so this is the only thing between one and a poisoned round. ⚠ A naive new status would zero the whole batch — the scorer demands total coverage, so an unrecognised status drops the claim and returns 0.0 for all 50. That exact failure happened in September: 93 of 100 claims were fine and every number came back 0.0.

0c — render the prompt in Python, and be the dispatcher. Both observed delivery bugs were shell the middleman model wrote at run time, differently each run; 13 of 561 sessions began with no task at all. Python cannot improvise a broken heredoc. ⚠ The prompt text stays the optimizer's to rewrite; the code that fills and launches it does not.

Phase 1 — the two boxes, the boundary itself pending ● changed
What changed: two corrections landed here from the round-2 review — the bypass flag splits by path, and the read-list warning pointed at the wrong file.

1a — pin the engine. See build item 1. The pin is only real if the import path changes too.

1b — what the program's box can see. Scratch space writable, the frozen spec and the snapshot read-only, a folder for the transcript. Everything else denied by absence and asserted denied. ⚠ The mounts do not cover the credential or the network: the box needs its own API access, so the network stays open to an allowlist, and the token must be passed by name rather than by value or it lands in the host command line and a log file.

What changed: the permission-bypass flag is passed in two places. We pass it ourselves for the program — so that fix is local and available now — and the shared engine passes it for the optimizer, which is the upstream half. An earlier version of this plan said it wasn't ours at all, which would have left the program wide open while the upstream diff looked like the fix.

1c — build the command per dispatch, not once at startup. Three inputs are only known later: the program version changes per round, the scratch space per claim, and the staged command has real machine paths baked into it that mean nothing inside a box. ⚠ It must key on the stage too — with the full pipeline, one command per claim would hand all three stages the same one, and the stages need different mounts. ⚠ A writable mount cannot be nested inside a read-only one on current Docker; the working example puts it at a sibling path for exactly this reason.

1d — keep the transcript. The lookup reaches into the host's own session folder, which inside a box is the box's and vanishes with it. ⚠ The failure is silent: the reference just goes empty while the run still reports success, so the check has to assert the reference is non-empty, not that the run succeeded.

1e — the optimizer's box. Copy the working example's mount discipline. ⚠ There is no ownership change to drop — an earlier version of this plan warned about one that does not exist in that code. What to actually avoid copying: it never deletes its temporary folder, so every round leaves one behind.

What changed: the read-list warning now points at the right file. See the gold-chain diagram — the release carries a pointer, and the answer key is the file it points at. A marker planted only in the release would pass while the program could still follow the pointer.

1f — one place that refuses to run uncontained. See build item 5. Plus a second refusal: reject any stage whose mount set has not been specified and tested, naming the stage. Without it, enabling the full pipeline silently runs two stages inside a boundary designed for neither, and the symptom would be a plausible answer rather than an error.

1g — the marker test. Plant markers where the secrets are and show a judging session cannot read them. ⚠ This mirrors the one read-oriented control that shipped — which asserts reads succeed. Across 15 existing seal tests, nothing asserts that a reachable path cannot be opened. That is the gap this closes.

Phases 2, 3 and 4 — the layers behind the boxes pending

Phase 2 — narrow what is exposed. Phase 1 makes things unreachable; Phase 2 reduces what is visible even where the mounts already deny it. It removes the look-around channel that actually fired in September — which turned out to be git state, not project context. The sessions listed filenames "based on the git status", and a working folder with no git history kills that at the source.

The critical here — and yes, exactly as you said: the folder is named by the program version. A single fixed folder cannot serve the now-editable judging instructions: their bytes differ per version, so one shared folder serves whichever version wrote it last, and two versions in the same run could execute the same instructions while the results say they ran different programs. Plausible answers both times, nothing downstream showing it. The cleanest form is already on disk — the per-round snapshot holds the instructions at the same path, is already read-only, and has no git history in it.

Phase 3 — pin the configuration. A fingerprint over the image digest, the mounts as actually rendered, the network policy and the session flags. ⚠ Read from the committed file, not the working copy — a sibling plan shipped exactly that defect, comparing a sheet against a stub that was editable in the same tree, so one session rewriting both passed.

Phase 4 — reset the run state. The lessons sheet is injected into every optimizer session and had never been reset between runs, while the code reasons as though a reset were guaranteed. ⚠ Sequential, not concurrent — which is what an earlier version failed to say, and what made a per-run clone look necessary. It is not: a clone buys namespace isolation for runs that overlap, and you never have two at once. One leftover the reset does not cover: version tags are repository-global, so a second run re-mints the first run's (question 12).

Why this happened, and the shape it keeps taking

The requirement existed verbatim, in three separate places before any of this was written. None of it shipped. It was traded away in a single commit, for a functionality reason, with no line in any plan and no comment on the cost — and then two later arguments locked the trade in, and a review blessed it under a "does it run" lens.

The one-sentence version, and the reason this plan is small: in every single instance, a mechanism that would have covered it already existed and was pointed somewhere else. That says re-aim what you have, not build another one.

Gotchas — things that already bit, or would have

The armed run's safety number proves nothing read this

The August run this plan leans on reports denied=0, and the write-up reads that as "the agent hit zero sandbox denials". But container mode has no per-call permission hooks at all, so nothing could be denied — the counter starts at zero and only moves when a hook ledger exists. The number is zero by construction.

⚠ This is the plan's own root-cause pattern — a mechanism pointed somewhere else, reporting green — sitting inside the evidence the plan uses to justify itself. It is now a row in the plan's root-cause table.

The substrate is less proven than it was cited as read this
  • The "212 passed" figure was your Mac with the container tests skipped — the real line is 212 passed / 15 skipped, and the 15 skips are the container tests. That plan had no VM run at all.
  • The seal test suite has not been re-verified since an August refactor; the last real container run predates it. So the plan re-runs it rather than citing it.
  • Its writable-mount ownership check is on file mode bits only — its own text calls that "a proxy for the property, not the property".
Do not inherit the working example's read list read this

rad-eval's read list grants the release files by pattern and the lessons sheet by name. That is correct for rad-eval — it is the optimizer's list, and the optimizer legitimately reads its own lessons and its training results. It is catastrophic for the program.

The code's own comment is the cleanest statement of the principle anywhere in the codebase: "This file contains gold labels. TRAIN gold is fully open to the optimizer (that is the mechanism by which it learns, not a leak); VAL gold is not." Correctly open to one, an answer key for the other — which is exactly why read scope has to be per principal.

How we will know it worked

What changed: a free dry run is now the first gate, and two gates that still demanded the old middleman-plus-subagent shape now assert the opposite.

Step 0a — costs nothing, run it first. Render every command for every combination of stage, profile, claim and program version. Start no container. Call no model. Then assert: every path in every command is a container path, with no host path anywhere; each stage either resolves a specified mount set or trips the stage refusal; no two dispatches share a command; the subagent tool is absent; the bypass flag is gone. This is the cheapest check in the plan and it covers the two defects most likely to survive review — a reused command, and an unhandled stage.

The gate that decides. The marker test, plus a control that must itself fail. A green where nothing was attempted is indistinguishable from a real seal, so every probe is enumerated from the command actually built, the mount list is compared exactly, and no mount source may be an ancestor of a forbidden path. ⚠ Markers go in the release and in every answer-key path reachable from it.
