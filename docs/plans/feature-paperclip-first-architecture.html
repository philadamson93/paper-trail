DECISION 1 · OQ6Evidence-item shape for schema 1.0 → 1.1

The call: how does one evidence item carry paperclip-vs-PDF provenance and a replayable locator? (Today an evidence item is {section, line, snippet}; the separate attestation object is a section-checklist, not a hits array — so it can't just be reused as a per-hit container.)

OptionWhat it meansCost
A — generalize (recommended)Add two optional fields: {section, line, snippet, source_mode?, locator?}. locator = /papers/(handle)/sections/(name).lines#L(n) for paperclip, pdfs/(citekey).pdf#page=(n) for PDF.Additive — zero migration. Every existing consumer keeps reading {section, line, snippet}; new fields are ignored until a consumer opts in.
B — new hits modelIntroduce a distinct attestation/hits object as the per-evidence container.Migrates 4 consumers: adjudicator + verifier + renderer + ledger. Heavier, reversible only with churn.
Decided 2026-06-27: Option A. Lighter touch, no consumer migration, and it still satisfies the Codex constraint that every persisted evidence item carries a deterministic replayable locator (so grounding never rests on map's opaque output).

Blast radius / why it gates Phase 3: this is the exact JSON both the new extractor-dispatch-paperclip.md and the renamed extractor-dispatch-pdf.md emit, and what the adjudicator/verifier/renderer/ledger consume. Choosing it after the prompts are written forces a rewrite of both prompts.

DECISION 2 · OQ7Does the adjudicator see source_mode?

The call: should source_mode (paperclip / pdf / pdf_ocr_fallback) ride along in the evidence JSON the adjudicator reads, or be stripped before adjudication?

OptionWhat it meansCost
A — inert metadata (default lean)Carry source_mode in the evidence the adjudicator sees; it applies the identical rubric regardless of provenance.Simplest — the adjudicator already ignores provenance. One guardrail: confirm the adjudicator prompt can't be biased by the field.
B — strictly blindOrchestrator adds/preserves source_mode outside the adjudication payload; the adjudicator never sees it.Stronger isolation, but the orchestrator must thread the field around the adjudicator call.
Decided 2026-06-27: Option A — carry it as inert metadata, with a one-line check in the adjudicator prompt that provenance must not affect the verdict.

Blast radius / why it gates Phase 3: determines whether source_mode goes into the per-claim dispatch payload (paper-trail.md ~L396) or is stripped first — and it couples with Decision 1: if locator/source_mode live on the evidence item, the adjudicator sees them unless explicitly stripped.

Gotchas

paperclip lookup is broken server-side

As of the 2026-06-24 smoke, lookup field value errors ("server closed the connection") on every field, including known-good PMC DOIs. Resolve coverage via search -s source instead. search now also requires an explicit -s source flag (the stale skill predates this).

paperclip search is fuzzy — gate every candidate

Search always returns N results, so a non-empty list is not a match. Gate each candidate on normalized-title-overlap of at least 0.6 AND year within plus-or-minus 2. The true match often sits at result #2-#3, not #1 (the ranker favors newer same-topic work) — scan the full top-N with -n 4. -s pmc already spans the bioRxiv/medRxiv preprint mirror.

Search arXiv by title for EVERY ref, not just explicit-eprint refs

The first Phase-1 pass undercounted (19 vs 27) because it searched -s arxiv only for refs carrying an explicit arXiv eprint field. Paywalled IEEE/MRM/CVPR papers with an arXiv preprint (the groundable surface) were wrongly marked external. Searching -s pmc AND -s arxiv by title for every ref recovered the 8 preprint hits.

False-positive handles silently ground against the wrong paper

chaudhari2018 was proposed as a 28th paperclip hit (arx_1808.04447) but has sub-0.6 title overlap and a divergent author list (5 vs 9) vs the cited MRM-2018 paper — it stays external. A handle that points at a different paper would silently ground Phase-3 claims against the wrong source, so the strict gate matters more in paperclip mode than PDF mode.

Coordination with the multi-cite + neighbor branch

The plan originally assumed Features 1+2 (feature/multi-cite-and-neighbor-claims) would land first as a 1.0 to 1.1 bump, then paperclip-first would take 1.2. In reality Features 1+2 are plan-only and the live schema is 1.0, so (decided 2026-06-24) paperclip-first takes 1.0 to 1.1 directly; Features 1+2 take 1.2 if they land afterward. Both branches touch the same paper-trail.md dispatch payload (around line 396); a later rebase needs a careful three-way merge.

paperclip map needs a search-results id, not bare handles

map --from RESULTS_ID consumes a saved search-results id — you can't point it at a papers/(handle)/ directly. Multi-cite extraction first builds/reuses a results id covering the cited + sibling papers (the Phase-1 search, or a fresh title search), then map --from id. Single-cite just reads the one handle via cat/grep/scan. Every persisted evidence item must carry a replayable grep/scan/cat locator — a bare map passage is a lead, not evidence.

Validation rules go in the schema/orchestrator, not validate_claims.py

validate_claims.py is the pre-dispatch manuscript-anchor / citekey-marker validator (Phase 3.1.5). Exit-JSON schema validation is orchestrator-inline per control_flow.md. SOURCE_MODE_MISSING/PAPERCLIP_HANDLE_MISMATCH belong in verdict_schema.md § Validation rules + the orchestrator's Phase-3.2 check; validate_claims.py is untouched.

The verifier prompt forbids re-search

The live verifier-dispatch.md allows only local cat/rg/sed. The paperclip verifier path is not a one-line source_mode slot — it needs source_mode+handle added to the verifier payload AND an explicit paperclip grep/cat command allowance against papers/(handle)/content.lines.
